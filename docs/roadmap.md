# Build Roadmap & App Map

AutoLedger is **one product** — a full-suite accounting and bookkeeping application — with three modules: accounting, capture (the bill inbox) and inventory. It was built as a suite of separately chosen apps (LedgerCore, AP-Flow, StockLedger); [Phase 33](#phase-33-as-delivered) merged them. Phases 0–1 built the platform every module shares — identity, tenancy, RBAC. Phase entries below keep the app names they were delivered under; that is history, not the current structure.

Phases are sequential. Where a **Gate** is listed, do not start the gated work first — ask before reordering.

## Phase 0, as delivered

The stack boots and browser → Express → PostgreSQL is connected. No business functionality exists.

**Landed:**

- `server/` — Express 5 + TypeScript, layer-first (`controllers/`, `services/`, `routes/`, `middleware/`, `db/`, `config/`, `utils/`, `__tests__/`)
- Strict TS config, plus `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax` and friends that `strict` does not include. `tsconfig.json` type-checks; `tsconfig.build.json` emits
- `pg` Pool singleton with an idle-client `error` listener
- Fail-fast environment parsing that reports every missing variable at once
- `errorHandler` + `notFoundHandler`; `ApiError` as the one client-visible error type
- `GET /api/v1/health` — a real `SELECT 1`, `200`/`503`
- Graceful shutdown on `SIGTERM`/`SIGINT`: stop accepting, evict idle keep-alive sockets, drain, `pool.end()`, forced exit after 10s
- `client/` — React 19 + Vite 8, typed API layer in `src/services/fetchServices.ts`, a status page proving the three tiers
- Vitest with `globals: true`; 4 tests passing (3 unit on app wiring, 1 integration against real Postgres)
- `docker-compose.yml` reduced to `postgres` + `redis`; `JWT_SECRET` deleted
- Strays removed: root `package.json`, `_metadata.json`

**Deliberately changed from the original Phase 0 scope:**

| Planned | Actual | Why |
|---|---|---|
| `server/Dockerfile`, `client/Dockerfile`, `entrypoint.sh` | Not built. Docker runs Postgres + Redis only; app processes run on the host | Dev-loop speed and native file watching. Containerising the app belongs with deployment, where a multi-stage production image — not a dev image with a source mount — is the real requirement |

**Also not built, and not owed until later:** `react-router-dom` (Phase 1, with the second page), `utils/money.ts` (Phase 3, with the first money column), `types/express.d.ts` and `req.user` (Phase 1), the migration runner and `npm run migrate` / `db:reset` (Phase 1).

## Phase 1, as delivered

You can register, sign in, stay signed in across reloads, switch organizations, and see a dashboard of real data. The tenancy boundary is enforced and tested.

**Landed:**

- Migration runner (`db/migrate.ts`) — sorted application, per-file transaction, `schema_migrations` ledger, session-level advisory lock, filename/gap validation, and a **SHA-256 checksum guard that refuses to run when an applied migration has been edited**. Plus `db/reset.ts`, `npm run migrate`, `npm run db:reset`
- `001_organizations_and_users.sql` — `organizations`, `users`, `organization_members`, `refresh_tokens`, the shared `set_updated_at()` trigger, `UNIQUE (LOWER(email))`, role and currency CHECKs, FK indexes
- `authService` (all SQL) — register in one transaction with `ON CONFLICT` slug allocation, login with a dummy-hash timing equaliser, refresh rotation via `DELETE … RETURNING` with reuse detection and family invalidation, switch-org, logout
- `middleware/auth.ts` (token-only, no DB round trip) and `middleware/rbac.ts` (`requireRole`)
- `utils/jwt.ts`, `utils/cookies.ts`, `utils/validate.ts` (hand-rolled, no zod), `utils/requireUser.ts`, `types/express.d.ts`
- `/api/v1/auth` (6 routes) and `/api/v1/organizations` (2 routes) — see [api.md](api.md)
- Client: `react-router-dom`, `AuthContext` (three-state machine), `OrgContext`, `ProtectedRoute`, `AppLayout` + `OrgSwitcher`, login/register/dashboard/404 pages, single-flight `fetchWithAutoRefresh`
- **91 server tests** (up from 4) including the cross-tenant isolation suite, and **12 client tests** — the client had no runner before this phase

**Deliberately changed from the original Phase 1 scope:**

| Planned | Actual | Why |
|---|---|---|
| `GET /auth/refresh` | `POST /auth/refresh` | Rotation is state-changing, and `SameSite=Lax` still sends cookies on a top-level cross-site navigation — a `GET` would be a logout-CSRF hole |
| `register` seeds the chart of accounts | Deferred to Phase 3 (was Phase 2 before the platform layer was inserted) | `accounts` belongs to LedgerCore, not the platform. LedgerCore's first phase inherits a backfill obligation |
| `refresh_tokens.token` | `refresh_tokens.token_hash` | A dump of the table must not yield usable sessions |
| — | Added `GET /organizations/members` | Phase 1 otherwise has no org-scoped table, so the mandatory cross-tenant isolation test would have had nothing to test and `rbac.ts` nothing to guard |

**Known gaps, deliberate:** no email verification (columns exist, nothing writes them); a revoked membership stays effective for up to 15 minutes, which is the trade the short access-token TTL buys ([architecture.md](architecture.md)).

AutoLedger's post-login landing page is now an app chooser, not a single dashboard. `AppLayout` was renamed `PlatformLayout` and now hosts two things: the chooser at `/`, and a per-app shell (`AppShell`) mounted at `/app/:appSlug`. The old dashboard content (identity, organization, membership, session) moved to `/account` — it is suite-level, not app-level, and does not belong on either the chooser or inside an app.

**Landed:**

- `server/src/config/apps.ts` — the static app registry, `as const satisfies readonly AppDefinition[]`, one entry per app in the [App map](#app-map) below
- `GET /api/v1/apps` — authenticated, not role-gated; returns the registry as-is (no per-org entitlement yet)
- Client: `apps/registry.ts` (slug → element, for route wiring only — display data comes from the API), `useActiveApp` hook, `AppChooserPage` at `/`, `AppShell` at `/app/:appSlug`, `AccountPage` at `/account` (renamed from `DashboardPage`)
- Nothing under any app slug has features yet. `AppShell` renders a header and an empty outlet for `ledger-core` (the only `'building'` app); every other slug redirects back to `/`

**Deliberately changed from the original module-based roadmap:**

The roadmap through Phase 15 used to describe one ERP with modules (inventory, procurement, MRP, payroll, QMS, CRM, EAM) all posting into a shared GL. That plan is replaced by the [App map](#app-map) below — seven separate portfolio applications, each demonstrating a different accounting or engineering skill, sharing one identity/tenancy platform and (for LedgerCore specifically) one GL. See [Dropped from scope](#dropped-from-scope).

**LLM integration is no longer out of scope.** The previous ruling ("Do not add an LLM dependency, API key, or provider SDK without an explicit decision recorded here first") is reversed by this entry: TaxGuard AI (Phase 13 at the time, **now Phase 16**) requires RAG over `pgvector` and an LLM/embeddings SDK. **No migration in this phase.** The app registry is a static code list, not a database table — there is no per-org entitlement to persist yet. If entitlement becomes real (e.g. a paid tier that unlocks specific apps), it becomes a migration then, not now.

## Phase 3, as delivered

LedgerCore has a general ledger. You can see a seeded chart of accounts, post a balanced journal entry, reverse it, and read a trial balance that proves the books balance — and an unbalanced entry cannot be written by *anything*, including raw SQL.

**Landed:**

- `002_ledger-core_accounts.sql` — `accounts` with a self-referencing `parent_id` (the chart is a tree), `is_postable` separating header rollups from leaves, `UNIQUE (org_id, code)`
- `003_ledger-core_backfill_chart.sql` — the default chart for every organization that had none, paying the backfill debt Phases 1–2 accrued
- `004_ledger-core_journals.sql` — `journal_entries` and `ledger_lines`, plus **five triggers**: two `DEFERRABLE INITIALLY DEFERRED` constraint triggers enforcing the balance invariant at `COMMIT`, a `BEFORE INSERT` guard rejecting postings to header accounts or to another tenant's account, and two `BEFORE UPDATE OR DELETE` triggers making posted rows immutable with SQLSTATE `0A000`
- The **44-account default chart** (34 postable leaves, 10 headers), seeded inside `register`'s existing transaction and including the tax and FX accounts Phases 8 and 11 will need — so neither inherits a backfill of its own
- `utils/money.ts` — the branded `Cents` type with a checked constructor, and the `pg` `BIGINT`-string parser. `as Cents` appears in that file and nowhere else
- `zod` adopted for LedgerCore, with a new `src/schemas/` layer and `utils/parseBody.ts` bridging zod errors to `ApiError(400)`. Phase 1's hand-rolled `utils/validate.ts` still serves `/auth` — an addition, not a rewrite
- `/api/v1` — accounts (4 routes), journals (4, including `POST /:id/reverse`), reports (trial balance). See [api.md](api.md)
- `express-rate-limit` on `/auth/login` and `/auth/register` — **debt carried since Phase 1, now paid**
- Client: Tailwind v4 + `lucide-react`, and LedgerCore's first three pages under `Pages/`
- **191 server tests** (up from 95) and **27 client tests** (up from 15), including `__tests__/accounting/ledgerConstraints.test.ts`, which bypasses the service entirely and asserts the *database* rejects unbalanced and mutated rows

**Deliberately changed from the original Phase 3 scope:**

| Planned | Actual | Why |
|---|---|---|
| `journal_entries.updated_at` | Dropped | The row is immutable, so the column could only ever equal `created_at`. Dead scaffolding implying a capability the table does not have |
| `journal_entries.org_id ON DELETE CASCADE` | `ON DELETE RESTRICT` | You cannot delete an organization that has posted journals. Correct accounting, and the only way cascade and the immutability trigger can coexist — a cascade would abort inside the trigger instead of failing cleanly at the parent |
| Currency columns in Phase 8 with the FX engine | Written from Phase 3 | The *engine* can wait; the *columns* cannot. Once a line exists without its native amount and rate, that information is unrecoverable |
| One trigger enforcing the balance | Two | A trigger on `ledger_lines` never fires for an entry with **no** lines, and "debits equal credits" is vacuously true of nothing. A second deferred trigger on `journal_entries` closes it |
| `MIGRATION_FILENAME` regex unchanged | Widened to allow `-` | `/^(\d{3})_[a-z0-9_]+\.sql$/` rejected `002_ledger-core_accounts.sql` — the app-tagged convention [schema.md](schema.md) mandates. Found before writing any migration |
| `pg` default `DATE` parsing | Global type parser returning a string | `pg` parses `DATE` at local midnight; `.toISOString()` then shifted every accounting date back a day at UTC+05:30. A `DATE` is a calendar fact, not an instant |

**Known gaps, deliberate:** the trial balance is the only report — P&L and balance sheet are Phase 4, along with fiscal periods, so nothing yet prevents posting into a closed month. Rate limiting is per-IP only, which a distributed attacker defeats; per-account tracking needs a shared store, which Redis (available since Phase 7) could back, but the limiter has not been rewired to use it — see [Phase 7, as delivered](#phase-7-as-delivered)'s "Deliberately not built" for why. The FX columns exist but every line is written at rate 1 in the org's base currency until Phase 8. `created_by` is recorded on every entry but there was no audit trail yet at this point in the build — that gap is closed by [Phase 5, as delivered](#phase-5-as-delivered), below.

## Phase 3.5, as delivered

LedgerCore has a front door. A user who registers and picks LedgerCore for the first time is walked through a one-time onboarding wizard — workspace name, legal name, industry, base currency, fiscal year start, books start date, an optional cash account — and lands on a dashboard instead of a bare chart of accounts. The chart-of-accounts/journals/trial-balance tab strip is replaced by a sidebar with room for Reports and Settings.

**This is a half-step, not a renumbering.** It slots between the delivered Phase 3 and the unstarted Phase 4, and it changes no phase number anywhere in this document. Phase 4 is unaffected and unstarted: **no `fiscal_periods` table, no period close/lock, no posting-into-a-closed-period guard, no P&L, no balance sheet exist after this phase.** This phase stores a fiscal-year *setting*, consumed by report queries in application code — it creates no period rows and enforces no lock.

**Landed:**

- `005_ledger-core_settings.sql` — `ledger_settings` (one row per organization, keyed by `org_id`), and a composite `UNIQUE (org_id, id)` on `accounts` so `ledger_settings.cash_account_id` carries a **composite FK** `(org_id, cash_account_id) → accounts (org_id, id)` — a cross-tenant cash account is rejected by the database, not only by a service check. See [study/postgresql/composite-foreign-keys-for-tenancy.md](../study/postgresql/composite-foreign-keys-for-tenancy.md)
- `settingsService` — `getSettings` (a missing row means "not onboarded," never a 404), `completeOnboarding` (one transaction, idempotent — resubmitting overwrites rather than erroring), `updateSettings` (refuses to write until onboarding has completed once)
- `organizationService.updateOrganization` — new, takes an optional transaction client so `completeOnboarding` can write the organization's name and base currency in the same transaction as its LedgerCore settings
- **The base-currency lock**: changing `baseCurrency` once any `ledger_lines` row exists is rejected with `422` — those rows are immutable and stamped with their currency at write time, so a retroactive change would silently invalidate every posted line
- `dashboardService.dashboardSummary` — position (assets/liabilities/equity/cash/`currentEarningsCents`/`equationHolds`), year-to-date and month-to-date performance, a 6-point gap-filled trend, recent entries, and the integrity check, aggregated from raw `ledger_lines` on every request via `FILTER`-clause aggregates and a `generate_series` scaffold — see [study/postgresql/aggregating-a-ledger.md](../study/postgresql/aggregating-a-ledger.md). **No summary table**, same rule as the trial balance
- `/api/v1/settings` (3 routes) and `GET /api/v1/reports/dashboard`; `PATCH /api/v1/organizations` (new, platform-layer — organization name and base currency are platform fields, not LedgerCore ones)
- Client: `LedgerCoreSidebar`, `LedgerSettingsContext`, an onboarding wizard (`OnboardingPage`, 3 steps, discriminated-union step state), `DashboardPage` with a hand-rolled inline-SVG `TrendChart` (no charting library — rule 14), `SettingsPage`, and `ReportsPage` (trial balance live, P&L/balance sheet honestly marked "Phase 4," not linked to a stub)
- **230 server tests** (up from 191) and **41 client tests** (up from 27), including both modules' cross-tenant isolation suites

**Deliberately changed from the original plan:**

| Planned | Actual | Why |
|---|---|---|

## Phase 4, as delivered

The last piece of "LedgerCore GL completion" as the phase table originally scoped it — 3.9 paid off the AR/AP subledger line item early, so this phase is narrower than its original box: fiscal periods with close/lock, a database-enforced posting guard, and the two remaining live statements, P&L and the balance sheet.

**Migrations `015`–`016`:** `015` adds `fiscal_periods` and the project's first `CREATE EXTENSION` (`btree_gist`) — required to mix a plain-equality tenant column into a GIST exclusion constraint alongside a `daterange` overlap operator. `ex_fiscal_periods_no_overlap` (`EXCLUDE USING GIST (org_id WITH =, daterange(starts_on, ends_on, '[]') WITH &&)`) makes two overlapping periods in one organization physically impossible to insert, race-free — closing the exact "check, then write" race a service-level pre-check alone would have. `016` adds `assert_period_open()`, a plain `BEFORE INSERT` trigger (not deferred) on both `journal_entries` and `ledger_lines`, rejecting any posting dated inside a `CLOSED` or `LOCKED` period. See [study/postgresql/exclusion-constraints-and-gist.md](../study/postgresql/exclusion-constraints-and-gist.md).

**The close/lock lifecycle is a three-value FSM** (`FISCAL_PERIOD_TRANSITIONS`): `OPEN -> CLOSED`, `CLOSED -> OPEN | LOCKED`, `LOCKED -> ` nothing. `LOCKED` is the first genuinely terminal state anywhere in the codebase's FSMs — `VOID` on invoices/bills is also a dead end, but for the opposite reason (the correction already happened); `LOCKED` is a dead end because the entire point of locking is the promise that nothing will ever happen to the period again. Locking must pass through `CLOSED` first — there is no `OPEN -> LOCKED` edge — so the FSM itself enforces that a period was reviewed before it becomes permanent. See [study/architecture/document-lifecycle-fsm.md § A genuinely terminal state](../study/architecture/document-lifecycle-fsm.md).

**The posting guard is checked twice, like the balance invariant.** `journalService.createEntryOnClient` (the single write path every document — manual journals, invoice issuance, bill approval, payments — posts through) calls `fiscalPeriodService.assertPeriodOpenOnClient` before writing; `reverseEntryOnClient` writes `journal_entries`/`ledger_lines` directly rather than delegating to `createEntryOnClient`, so it carries its own call to the same guard. Migration 016's trigger is the independent, second layer — the service being correct is not the reason a closed month stays closed. A date covered by no period at all is treated as open: an organization that has never generated periods keeps posting without any change in behavior.

**`reportService.profitAndLoss`/`balanceSheet`**, both aggregated from raw `ledger_lines` on every request — no summary table, the same discipline the trial balance and dashboard already follow. The P&L splits Revenue and Expense by type-aware sign (never a raw `debit − credit`, which would show revenue as negative) and by code prefix for COGS (the `5xxx` range — not a sixth account type, rule 12 stays exactly five). The balance sheet's `equity.retainedEarningsCents`/`currentEarningsCents` are **derived**, computed as `SUM(revenue) − SUM(expense)` split at the fiscal year boundary, never read from a posted account `3200` — LedgerCore posts no year-end closing entry, so there is nothing else they could be derived from. See [study/postgresql/aggregating-a-ledger.md § Deriving a P&L and a balance sheet from raw lines](../study/postgresql/aggregating-a-ledger.md).

**`/api/v1/fiscal-periods`** (6 routes: list, get, generate, close, reopen, lock — `lock` is `OWNER`-only, the rest `OWNER`/`ADMIN`, reading open to any member) and **`GET /reports/profit-and-loss`** / **`GET /reports/balance-sheet`** (2 routes, any member). Full detail: [api.md](api.md). Client: `FiscalPeriodsPage` (a register with per-status actions and a `ConfirmDialog` gating only `Lock`, the one irreversible action — `Close`/`Reopen` act immediately, both being reversible), `ProfitAndLossPage`, `BalanceSheetPage` (both linking postable account names into their ledgers, mirroring the trial balance); `ReportsPage`'s two disabled "Phase 4" placeholder cards are now real links.

**Tests: 490 server tests** (up from 442) — `fiscalPeriods.test.ts`, `fiscalPeriodConstraints.test.ts` (the raw-SQL proof that the exclusion constraint and CHECKs hold independently of the service), `periodLock.test.ts` (the posting guard, exercised through manual journals, reversals, and invoice issuance alike, plus the trigger-path proof bypassing the service), `statements.test.ts` (a non-trivial fixture proving `Assets = Liabilities + Equity` by integer equality, an `information_schema` assertion that no summary table exists anywhere, and a cross-check that the P&L's net income for a fiscal year equals the balance sheet's current-period earnings at that year's end) — each carrying its own cross-tenant isolation case. **120 client tests** (up from 107).

**Deliberately not built:** no year-end closing journal entry — retained earnings stays derived indefinitely unless one is added later, and an organization that manually posts its own closing entry into `3200` will see that year's earnings counted twice, a stated and accepted gap rather than a guarded one. Quarterly or 4-4-5 fiscal calendars — `fiscal_periods.period_number` is capped at 12 monthly periods by CHECK. No per-period P&L drilldown, no PDF export, no audit trail (Phase 5, delivered since — see [Phase 5, as delivered](#phase-5-as-delivered), immediately below). Period boundaries and every date comparison here use UTC calendar dates, ignoring `ledger_settings.timezone`, matching aging and every other date-bounded report in this codebase.

## Phase 5, as delivered

Shared infrastructure, not a LedgerCore-only phase — the trail spans every app via `app_slug`, and closes the compliance gap every prior phase entry has flagged: **"no audit trail yet, no compliance claim should be made before it lands."** It has landed.

**Migrations `017`–`018`, platform-level (no app-slug tag).** `017` creates `audit_logs` — a `BIGINT GENERATED ALWAYS AS IDENTITY` primary key rather than this schema's usual UUID (a log's defining property is arrival order, which a UUID carries none of), `txid` (`pg_current_xact_id()`) grouping every row one transaction wrote, `org_id`/`app_slug`/`table_name`/`row_id`/`operation`/`old_row`/`new_row`/`changed_keys`/`actor_user_id`/`client_ip`/`created_at` — plus `audit_row_change()` (the generic `to_jsonb(NEW)`/`to_jsonb(OLD)` capture trigger, one function shared by every audited table) and `reject_audit_log_mutation()` (the same `0A000` immutability treatment `journal_entries` already has). `018` attaches `audit_row_change()` as an `AFTER INSERT OR UPDATE OR DELETE` trigger to 16 tables — every LedgerCore financial table plus `organizations`/`organization_members`. Deliberately not audited: `users`/`refresh_tokens` (a password hash or session credential has no business inside a JSONB snapshot) and `schema_migrations`.

**`org_id`, `row_id`, and `actor_user_id` carry no `REFERENCES`** — the one deliberate, documented exception to guardrails rule 8 anywhere in this schema. An audit row has to outlive the organization, row, and user it describes; a cascading or restricting FK would either destroy the very history it should preserve, or make deletion of an audited row's parent permanently impossible. See [study/architecture/append-only-audit-trails.md](../study/architecture/append-only-audit-trails.md).

**The actor and client IP reach a trigger that cannot see `req` via `AsyncLocalStorage` and a transaction-local session variable.** `middleware/requestContext.ts`'s `attachRequestContext` opens a per-request context — mounted first in `app.ts`, before `cors` — and `middleware/auth.ts`'s `authenticate` fills in `userId`/`orgId` on it once the access token verifies. `db/transaction.ts`'s new `beginTransaction`/`withTransaction` publish that context into PostgreSQL immediately after every `BEGIN`, via `set_config('app.current_user_id', ..., is_local := true)` — the *function* form, not `SET LOCAL`, because only the function form accepts its value as a genuine bind parameter (guardrails rule 4). `is_local := true` is what makes this safe on a connection pool: the setting is discarded at `COMMIT`/`ROLLBACK`, so it can never leak from one pooled request into the next. See [study/node-express/async-local-storage-request-context.md](../study/node-express/async-local-storage-request-context.md) and [study/postgresql/audit-triggers-and-session-variables.md](../study/postgresql/audit-triggers-and-session-variables.md).

**Every write transaction in the codebase was touched to make this possible, not just LedgerCore's.** The 20 pre-existing `client.query('BEGIN')` call sites, across `authService`, `organizationService`, and ten `ledger-core` services, became `beginTransaction(client)`. The 10 single-statement writes that previously ran directly on `pool` (`accountService`/`customerService`/`vendorService`'s `create`/`update`, `invoiceSettingsService.updateInvoiceSettings`, `settingsService.updateSettings`, `invoiceService.deleteInvoice`, `billService.deleteBill`, `organizationService.updateOrganization`'s default path) now run inside `withTransaction(...)` — every write, not only the ones that already happened to transact, now has a transaction for the audit context to attach to.

**`/api/v1/audit-logs`** (2 routes: list, get-one — both `OWNER`/`ADMIN` only, deliberately narrower than `/reports`/`/fiscal-periods`, since the trail records what an `ACCOUNTANT` did and the bookkeeper doesn't hold the key to their own log). Mounted platform-level, not under `/ledger-core` — `app_slug` on each row carries the app namespace instead (guardrails rule 16). The list omits `oldRow`/`newRow`; the detail route returns both, plus `changedKeys` for an UPDATE. A non-numeric or cross-tenant `id` returns `404`, never `400`/`403`. Full detail: [api.md](api.md). Client: `AuditLogPage` — filterable by app/table/operation, click-to-expand before/after diff, reached from LedgerCore's rail (the natural home until a second app ships a UI, since the trail itself is platform-wide).

**`npm run verify:integrity`** — `db/integrity.ts` (pure, importable) + `scripts/verifyIntegrity.ts` (the CLI tail, split out specifically so importing the checker from a test never exits the test process). Three checks, each unscoped by `org_id` on purpose — the single other sanctioned exception to rule 1 in the codebase, isolated in `src/db/` so nothing request-serving can import it by accident: total debits equal total credits across the whole database; every journal entry balances on its own (`GROUP BY` + `HAVING`, not `WHERE`); no `ledger_lines` row is orphaned or claims the wrong `org_id` (a `LEFT JOIN`/`IS NULL` anti-join, not `NOT IN`, which has a NULL-handling trap). `server/src/__tests__/integrity.test.ts` proves the checker **can fail** — the roadmap's own stated requirement — by disabling every user trigger on `journal_entries`/`ledger_lines` (`ALTER TABLE ... DISABLE TRIGGER USER`), inserting the exact broken rows the schema normally prevents, and re-enabling in a `finally`. See [study/postgresql/integrity-checking-a-ledger.md](../study/postgresql/integrity-checking-a-ledger.md).

**Tests: 519 server tests** (up from 490) — `integrity.test.ts` (4 cases, including the two that manufacture broken data), `platform/auditTrail.test.ts` (10 — capture correctness, org scoping, the `users`/`refresh_tokens` exclusion, the immutability guard, cross-tenant isolation), `platform/auditActor.test.ts` (6 — actor/IP attribution end-to-end through HTTP, a multi-table transaction sharing one `txid`, a null actor for a request-less write, and the pooled-connection non-leak case), `platform/auditLogs.test.ts` (9 — filtering, role gating, cross-tenant isolation on both the list and the detail route). **125 client tests** (up from 120) — `ledgerCoreAuditLog.test.tsx`.

**Deliberately not built:** retention or partitioning on `audit_logs` — a stated, accepted cost, not an oversight: registering an organization now writes roughly 46 audit rows via the default-chart seed, and a 20-line journal entry writes 21. No hash-chaining or other tamper-evidence beyond the immutability trigger — a table-owner-privileged actor can still `ALTER TABLE ... DISABLE TRIGGER` first, exactly as the checker's own test does; this trail is a strong guarantee against application-level tampering, not an absolute one, and no compliance claim should overstate that. No scheduled/continuous integrity check — `verify:integrity` runs on demand until Phase 7's background jobs exist. **Every prior phase's "no audit trail (Phase 5)" caveat elsewhere in this document, in `ledger-core.md`, and in `CLAUDE.md` has been corrected with a pointer to this section** — the historical claim ("this phase didn't build it") stays accurate; only the implication that it's still true today has been removed.

## Phase 6, as delivered

Closes LedgerCore's last GL-completion gap — reconciling the ledger against a real bank statement, with confidence-scored matching so most lines never need a human decision.

**Migration `019`, LedgerCore-tagged.** Three tables: `bank_statement_imports` (one row per uploaded CSV — file name, delimiter, date format, row/imported/duplicate counts, and an optional stated closing balance), `bank_transactions` (one row per parsed line, `amount_cents` **signed** — positive is money in, negative out, unlike a `ledger_lines` row which always has exactly one side populated — and a `UNIQUE (org_id, dedupe_hash)` constraint that makes re-importing a statement idempotent), and `bank_match_suggestions` (up to 5 scored candidates per unmatched line, deleted and regenerated wholesale on every rescore, deliberately **not** audited since it's disposable derived data). `bank_transactions` gets the same `to_jsonb` row-diff immutability carve-out `payments` (014) has — only its match state may change, `DELETE` always rejected — because a bank line is a record of fact from a downloaded statement. See [study/postgresql/idempotent-ingestion-and-dedupe-hashes.md](../study/postgresql/idempotent-ingestion-and-dedupe-hashes.md).

**Nothing new was installed.** The CSV parser (`utils/csv.ts`, a hand-written two-pass state machine — quoted commas, embedded newlines, doubled-quote escaping, BOM stripping, delimiter sniffing outside quotes), the flexible date parser (`utils/dateParse.ts`, `ISO`/`DMY`/`MDY` plus month-name forms), the untrusted-text money parser (`utils/money.ts`'s new `parseMoneyText`, asymmetric dot/comma separator resolution, accounting parentheses and `CR`/`DR` notation, no intermediate float), and the Levenshtein distance implementation (`utils/levenshtein.ts`, a rolling-array `O(min(m,n))`-space DP) are all hand-written, exactly as this phase's roadmap entry always specified. A CSV statement arrives as a JSON string field, not a multipart upload — file storage stays a later phase's problem (Phase 10 when this was written; reassigned to [Phase 9.5](#phase-95-as-delivered) on 2026-09-10, delivered 2026-09-10) — capped by `MAX_CSV_CHARS` (900,000 characters) comfortably under the 1MB JSON body limit.

**The 40/30/30 confidence engine** (`utils/matchScore.ts`) scores each unmatched line against open invoices (positive amounts) or bills (negative amounts) dated within ±30 days: 40 points for an exact integer-cent amount match, up to 30 for date proximity (stepped down by whole days apart, not continuous decay), up to 30 for counterparty text similarity (the document's number or the counterparty's name found in — or Levenshtein-similar to — the bank memo). A hand-tuned noise floor (0.5 similarity) keeps coincidental letter overlap between unrelated strings from reading as real evidence; `AUTO_MATCH_THRESHOLD` (85) is set high on purpose, since a false auto-match posts a real payment against the wrong document while a missed suggestion just costs one extra click. Every score is stored with its full breakdown (`{ amount, date, counterparty }`, each with `points`/`maxPoints`/a human-readable `reason`), so a suggestion is explainable on screen, never a bare number. See [study/architecture/fuzzy-matching-and-confidence-scoring.md](../study/architecture/fuzzy-matching-and-confidence-scoring.md).

**Matching posts through the existing payment path, never a direct GL write.** `paymentService.createPayment`/`voidPayment` were split into `createPaymentOnClient`/`voidPaymentOnClient` (the transaction-taking half) plus a thin wrapper that owns the connection — mirroring the split `journalService.createEntryOnClient` already had — so `bankMatchService.matchTransaction` can post a payment and update the bank line's status inside one transaction, and `unmatchTransaction` can void that payment and revert the line inside another. `BANK_TRANSACTION_TRANSITIONS` (`UNMATCHED -> MATCHED | IGNORED`, `MATCHED -> UNMATCHED`, `IGNORED -> UNMATCHED`) is the first FSM in this codebase where a non-terminal reverse edge carries a GL side effect rather than touching only its own row — and since `/unmatch` and `/unignore` both legally land on `UNMATCHED` by the shared table alone, `unmatchTransaction` layers its own narrower `status === 'MATCHED'` check on top of the FSM check rather than in place of it. A bank line settles **at most one document**, in full or in part — never a batch of several. See [study/architecture/document-lifecycle-fsm.md § A reversible state whose reverse edge carries a GL side effect](../study/architecture/document-lifecycle-fsm.md).

**`/api/v1/bank-imports`** (3 routes: list, get-one, import) and **`/api/v1/bank-transactions`** (7 routes: list, get-one, rescore, match, unmatch, ignore, unignore) — every mutation gated `OWNER`/`ADMIN`/`ACCOUNTANT`, the same set `/payments` uses, since matching and unmatching each post or void a real journal entry. **`GET /reports/bank-reconciliation`** compares a bank account's posted GL balance against its imported statement lines, both computed independently and compared by integer equality — but unlike `/ar-aging`/`/ap-aging`'s `reconciles`, a `false` result here is a **completeness** claim about the imported statement history, not a **correctness** claim about the books: the two sides describe different realities (this system's own postings vs. a CSV a human chose to upload), so the far more common cause of disagreement is a missing import, not a bug. See [study/postgresql/subledger-reconciliation-and-aging.md § Bank reconciliation](../study/postgresql/subledger-reconciliation-and-aging.md). Full detail: [api.md](api.md). Client: `BankImportPage` (the CSV's text goes straight into the JSON body, read via `FileReader`, never a multipart upload), `BankTransactionsPage` (the approval queue — status tabs, inline suggestion cards with `MatchScoreBadge` and the three-reason breakdown, one-click Accept at or above the threshold, `ConfirmDialog`-gated Match below it and Unmatch always), `BankReconciliationPage`; a new "Banking" sidebar group.

**Tests: 645 server tests** (up from 519) — `csv.test.ts` (14), `dateParse.test.ts` (19), `levenshtein.test.ts` (13), `matchScore.test.ts` (10), 17 new cases in `money.test.ts` for `parseMoneyText`, `bankConstraints.test.ts` (13, raw-SQL proof of the dedupe/immutability/FK constraints, including the cross-tenant dedupe-scoping case), `bankImports.test.ts` (12, including the roadmap's own acceptance criterion as a named test — `'the same statement imported twice yields one set of rows'` — and two cross-tenant cases), `bankMatching.test.ts` (18, including a deterministic 100-line fixture proving **zero false auto-reconciles above the threshold** — the roadmap's other acceptance criterion — plus the closed-period interaction and two cross-tenant cases), `bankReconciliation.test.ts` (8, including a cross-tenant case). **139 client tests** (up from 125) — `ledgerCoreBankImport.test.tsx`, `ledgerCoreBankTransactions.test.tsx`, `ledgerCoreBankReconciliation.test.tsx`. `npm run verify:integrity` passes after the full suite runs, confirming the matching engine posted only balanced entries throughout.

**Deliberately not built:** a bank line settling more than one document, or several lines settling one, in a single match. Bank feeds, Open Banking, OFX/QIF/MT940 — CSV only. Multi-currency statements. Posting a journal entry directly from an unmatched line for bank fees or interest — `IGNORE` covers that case for now. No new dependency of any kind — the CSV parser, date parser, money-text parser, and Levenshtein distance are all hand-written, exactly as this phase's roadmap entry specified from the start.

## Phase 7, as delivered

Shared infrastructure, not owned by any one app: a real background-job system on Redis, and the first consumer of it — outbound financial-event webhooks, built on a transactional outbox so a notification can never be lost to a crash between commit and send.

**Two new dependencies, exactly as scheduled since Phase 0.** `bullmq` (^6.3.4) and `ioredis` (^6.0.0) — nothing else. `REDIS_HOST`/`REDIS_PORT`/`REDIS_DB` join `server/.env`, all optional with defaults matching `docker-compose.yml`; the Redis container (provisioned since Phase 0, unused until now) gains a healthcheck. `npm run worker` (`tsx watch src/worker.ts` in dev, `worker:start` against the built output) starts a second process — its own event loop, its own `pg` pool, its own crash domain — consuming three queues (`integrity-check`, `outbox-drain`, `webhook-deliver`) plus a fourth, `dead-letter`, that nothing consumes by design: it exists to accumulate visibly rather than requiring an operator to know to look inside a queue's own failed set. Retry policy is 5 attempts with exponential backoff from 1s outside tests; a job that exhausts its retries is enqueued to `dead-letter` by the worker's own `'failed'` listener, not by BullMQ itself. See [study/architecture/background-jobs-and-queues.md](../study/architecture/background-jobs-and-queues.md).

**The transactional outbox closes the gap guardrails rule 5 has named since Phase 0** — no post-`COMMIT` follow-up work in the same function, which an HTTP call to a webhook receiver structurally cannot honor if made inside the transaction (it would hold a database connection open across a network round trip) or after it (a crash in the gap loses the notification with no durable record it was ever supposed to happen). Migration `020`, platform-tagged: `outbox_events` (written on the *caller's own transaction client* — `outboxService.emitEvent(client, ...)`, never `pool` — so the event commits or rolls back atomically with the financial fact it describes), `webhook_endpoints` (a tenant's registered receivers, `secret` stored in plaintext because the server must reproduce the exact HMAC key on every send — never selected into any API response), and `webhook_deliveries` (one row per event per subscribed endpoint, tracking every attempt). A repeatable job drains the outbox every 5 seconds: `FOR UPDATE SKIP LOCKED` claims a batch of unpublished events (the same primitive, at larger scale, `refresh_tokens` rotation uses at the single-row scale — see [study/postgresql/transactions-isolation-pooling.md](../study/postgresql/transactions-isolation-pooling.md)), fans each out to its org's active subscribed endpoints as `PENDING` deliveries (`UNIQUE (event_id, endpoint_id)` + `ON CONFLICT DO NOTHING` makes the fan-out itself idempotent), and a second pass in the same drain re-enqueues any `PENDING` delivery whose Redis job looks lost — the compensation for the unavoidable gap between committing the delivery row and successfully calling `queue.add()`. This is honest **at-least-once** delivery, not exactly-once: a receiver is expected to dedupe on `deliveryId`. Full mechanism: [study/architecture/transactional-outbox.md](../study/architecture/transactional-outbox.md).

**Five events, chosen to be testable end to end rather than exhaustive:** `invoice.issued`, `bill.approved`, `payment.recorded` (emitted from `paymentService.createPaymentOnClient` specifically — not the thin `createPayment` wrapper — so a payment born from a bank match, Phase 6's `bankMatchService.matchTransaction`, fires the identical event a manually-posted payment does), `fiscal_period.closed` (on `CLOSED` only, never on `LOCKED` or on reopen), and `bank.large_unmatched` (a new `ledger_settings.unmatched_alert_threshold_cents` column, migration `021`, `DEFAULT 0` meaning disabled for every organization including ones that predate the migration; a signed bank-line `amount_cents` compared by `Math.abs` against the threshold, so a large outflow alerts exactly as a large inflow does). There is deliberately no `payment.voided` event and no endpoint-level custom-event support — inventing either was judged a later phase's call, not this one's.

**HMAC-SHA256 signing, and a write-time SSRF guard on every endpoint URL.** Every delivery carries `X-AutoLedger-Signature: sha256=<hex>`, computed over `${timestamp}.${rawBody}` — folding the timestamp into the signed material gives replay protection for free, since a captured request can't be replayed with a fresh timestamp without knowing the secret. `assertDeliverableUrl` rejects `localhost`/`*.internal`, every private/reserved IPv4 range including the cloud metadata address `169.254.169.254`, embedded credentials, and non-`https` outside development; `redirect: 'manual'` on every outbound `fetch` stops a receiver's own redirect from silently reaching a private address the guard would have rejected as the original URL. DNS rebinding — a hostname re-pointed to a private IP *after* the write-time check — is a recorded, accepted gap: closing it needs a resolve-then-connect-to-the-resolved-IP flow Node's built-in `fetch` doesn't expose a hook for. See [study/security-auth/webhook-signing-and-ssrf.md](../study/security-auth/webhook-signing-and-ssrf.md).

**`/api/v1/webhooks`** (6 routes: list, create, get-one, update, `OWNER`-only delete, `OWNER`-only rotate-secret) and **`/api/v1/webhook-deliveries`** (3 routes: list, get-one, retry) — both platform-level, not namespaced under `/ledger-core`, mirroring `/audit-logs` (guardrails rule 16: an app-owned event still lands in shared, platform-owned machinery). The secret is present in exactly two responses, `create` and `rotate-secret`, and never elsewhere — a page reload loses it by design, which the client's `WebhooksPage` states in a dismissible one-time panel. `POST /:id/retry` is legal only from `FAILED` (`409` from `PENDING` or `DELIVERED`) and returns `202`, since the send is accepted for processing, not performed synchronously. Full detail: [api.md](api.md). Client: `WebhooksPage` (endpoint CRUD, the secret-reveal panel, `ConfirmDialog`-gated rotate and delete), `WebhookDeliveriesPage` (server-side-filtered delivery log, expand-to-payload, Retry gated to `FAILED` rows), a new "Automation" sidebar group.

**Phase 5's own recorded debt is paid here too:** `verify:integrity`'s three whole-database checks now also run automatically once a day via the worker's job scheduler, not only on demand — see [Phase 5, as delivered](#phase-5-as-delivered) above.

**Tests: 717 server tests** (up from 645) — `platform/queue.test.ts` (job processing, retry-then-dead-letter, jobId dedup), `platform/webhookEndpoints.test.ts` (31, including the URL-guard and signature unit cases and the mandatory cross-tenant suite), `platform/outboxDrain.test.ts` (8, including the transaction-rollback-leaves-no-row proof and a cross-org fan-out isolation case), `platform/webhookDelivery.test.ts` (17, `fetch` stubbed at the boundary per [testing.md](testing.md), including the signature-verification and no-secret-in-body assertions, plus one case against the real worker wiring proving exhausted retries mark a delivery `FAILED` and dead-letter the job), `ledger-core/outboxEmission.test.ts` (11, one case per event type plus the rollback-emits-nothing proof for a locked-period invoice issue), plus updates to `health.test.ts` for the new `redis` block. **144 client tests** (up from 139) — `ledgerCoreWebhooks.test.tsx`, `ledgerCoreWebhookDeliveries.test.tsx`. The integration suite now requires `docker compose up -d redis` in addition to `postgres`; `globalSetup` flushes Redis database index 1 (never index 0) before the run, mirroring the existing `autodb_test`-not-`autodb` discipline.

**Deliberately not built:** Redis-backed per-account rate limiting — `constants.ts` has said "arrives with Redis in Phase 7" since Phase 3, and that specific claim is now corrected: it needs `rate-limit-redis`, which is not an approved Phase 7 dependency, so the login/register limiter stays per-IP. `POST /webhooks/:id/test` (a one-off send would bypass the outbox and be a second, untested delivery path). A `payment.voided` event, or any event type beyond the five named above. Per-endpoint retry-policy overrides. Retention or partitioning on `webhook_deliveries` — the same accepted, stated cost `audit_logs` carries since Phase 5. Full DNS-rebinding closure on the webhook URL guard (see above).

## Phase 8, as delivered

LedgerCore's last GL-completion phase: the multi-currency FX engine the schema has been carrying columns for since Phase 3 (`ledger_lines.currency_code`/`fx_rate`/`base_debit_cents`/`base_credit_cents`, written at rate 1 for every row until now). Five migrations, `022`–`026`, zero new dependencies.

**`022_ledger-core_fx_rates.sql` — exchange rates, org-scoped.** `fx_rates` keyed by `(org_id, from_code, to_code, rate_date)`, resolved as **the latest rate on or before** a date, never an exact match — a rate feed has weekend and holiday gaps. A rate row means "one unit of `from_code` buys `rate` units of `to_code`," always recorded foreign → base, so converting a native amount to base currency is always a multiplication, never an inversion. **Deliberately changed from the original Phase 8+ sketch in [schema.md](schema.md):** the sketch called for one global table with no `org_id`, reasoning an exchange rate is "a fact about the world." The phase as built makes it org-scoped instead — there is no external rate-feed integration (no approved outbound-API dependency, no key management), so a rate is reference data an organization enters for itself, and rule 1's "every query is scoped by `org_id`" is honored rather than carved out a second time. `rate` is `NUMERIC(18,8)` and stays a `string` end to end — on the wire and in TypeScript — converted through exactly one chokepoint, `utils/fxRate.ts`'s `rateNumerator`, never a bare `Number(rate) * cents`. See [study/postgresql/multi-currency-and-functional-currency.md](../study/postgresql/multi-currency-and-functional-currency.md).

**`023_ledger-core_base_currency_balance.sql` — base currency is what balances.** Redefines migration 004's `assert_journal_entry_balanced()` via `CREATE OR REPLACE FUNCTION` — `004` itself is not edited and its checksum is unchanged, since a `CONSTRAINT TRIGGER` resolves its function body by name at fire time, not at trigger-creation time. The native-currency sum check now fires only when an entry's lines share one `currency_code`; the base-currency sum check is now unconditional, on every entry, always — the invariant that actually protects the books once a second currency exists. A new CHECK, `chk_ledger_lines_base_matches_rate`, proves every line's `base = round(native × rate)` independently of the entry-level trigger, valid against the whole pre-existing table with **zero backfill**, since every row was already at rate 1.

**`024`/`025` — foreign-currency invoices, bills, and payments.** Each gains `fx_rate` and `base_*_cents` columns, resolved on every draft save (so a draft always shows an honest base-currency total) and **frozen** again at issue/approve/post, re-resolved for the actual posting date rather than trusted from an earlier save. `paymentService.createPaymentOnClient`'s realized-FX settlement is one computation — `imbalance = Σ(base debits) − Σ(base credits)` over a cash line at the settlement-date rate and one control line per allocation at *that allocation's own document's* frozen rate — with no direction-specific sign branch: the same subtraction produces a receivable-settled-high gain (credit `4910`) and a payable-settled-high loss (debit `6810`), because the RECEIVE/PAY asymmetry is already baked into which side of the ledger the lines were built on. One control line per allocation, not one blended line per payment, is what keeps a multi-document payment satisfying the per-line rate CHECK when its documents were frozen at different rates. `payment_allocations.base_amount_cents` is this codebase's one deliberate stored-not-derived exception — pinned at write time from two independently-frozen facts so the subledger ties to the GL to the cent, permanently, rather than depending on a conversion function never changing behavior. `trg_allocations_currency` enforces, independently of the service, that a payment may only settle documents in its own currency. See [study/architecture/realized-and-unrealized-fx.md](../study/architecture/realized-and-unrealized-fx.md) and [study/architecture/derived-vs-stored-state.md](../study/architecture/derived-vs-stored-state.md).

**`026_ledger-core_fx_revaluations.sql` — period-end unrealized revaluation.** `fx_revaluations`/`fx_revaluation_lines` — **deliberately no status column and no FSM**, unlike every other lifecycle table in this schema: a revaluation posts once and stays posted; a wrong one is corrected by the next period's revaluation, never edited or voided. `fxRevaluationService.runRevaluation` restates every open foreign-currency invoice/bill at the as-of rate through a **single** `6820 Unrealized FX Gain/Loss` account (unlike the realized `4910`/`6810` pair — one continuous economic estimate, not two kinds of event), using the identical imbalance-as-plug technique, and immediately posts a **second** entry reversing it, dated the calendar day after `asOfDate` — so a later realized settlement always compares against a document's original frozen rate, never a revalued carrying amount. `GET /reports/fx-exposure` runs the identical computation read-only, backing a preview the client shows before `POST /fx-revaluations` commits anything.

**`/api/v1/fx-rates`** (4 routes: list, `/latest`, upsert — overwrites on a repeat `(fromCode, toCode, rateDate)`, `OWNER`/`ADMIN`/`ACCOUNTANT` — and `OWNER`/`ADMIN`-only delete) and **`/fx-revaluations`** (3 routes: list, get-one, `OWNER`/`ADMIN`-only post — narrower than every other write route except `/fiscal-periods/:id/lock`, since a revaluation posts to the GL on someone's behalf). `GET /reports/fx-exposure` and both aging reports (`/ar-aging`/`/ap-aging`) now report in base currency, matching every other statement — for an organization with no foreign-currency documents this is numerically identical to the pre-Phase-8 figures. Full detail: [api.md](api.md).

**Bank reconciliation stays base-currency-only — a Phase 6 limit this phase does not lift.** A foreign-currency document is never offered as a match candidate, and a manually-chosen one is refused with `422`; multi-currency bank statements remain out of scope.

**Client:** `FxRatesPage` (delete gated by `ConfirmDialog`), `FxExposurePage` (post gated by `ConfirmDialog` — the one irreversible action on the page, matching `FiscalPeriodsPage`'s Lock), `FxRevaluationsPage`, a currency selector on `NewInvoicePage`/`NewBillPage` with a live resolved-rate and base-total preview (a `422` from the rate lookup renders inline with a link to Currency → Rates, never a silent fallback to rate 1), `PaymentDialog` showing the settlement-date rate and an estimated realized gain/loss, a new Currency sidebar group (Rates, Exposure, Revaluations).

**Tests: 776 server tests** (up from 717) — `fxRate.test.ts` (unit, the `rateNumerator`/`convertToBase` arithmetic), `ledger-core/fxRates.test.ts`, `fxLedgerConstraints.test.ts` (raw-SQL proof that base-currency balancing holds independently of `journalService`), `fxDocuments.test.ts`, `fxRealized.test.ts` (including the named test reproducing [docs/accounting.md § 3](accounting.md#3-realized-fx--the-worked-example)'s worked example to the paisa — the phase's stated acceptance criterion — and its payable mirror case), `fxPaymentConstraints.test.ts`, `fxRevaluation.test.ts` (including the next-day-reversal proof and a case proving the balance sheet still balances after a revaluation) — each carrying its own cross-tenant isolation case. **150 client tests** (up from 144).

**Deliberately not built:** an external rate-feed integration — rates are entered by hand or imported as a batch (`fx_rates.source` distinguishes them), but nothing calls out to a live provider; `source = 'IMPORT'` exists so a later phase can add one without a schema change. FX on bank matching (see above). A currency on an *account* itself — a cash account's balance is reported in base currency even though it may have received lines in several currencies over its life; forcing one currency per account was rejected as out of scope. Consolidation-style translation of a whole subsidiary's trial balance — this phase revalues open AR/AP balances, not a full set of books. A settings-page UI for the three FX posting accounts (`realizedFxGainAccountId`/`realizedFxLossAccountId`/`unrealizedFxAccountId`) — exposed through `GET`/`PATCH /settings` same as every other setting, but with no dedicated form control yet, matching the existing gap around `unmatchedAlertThresholdCents` since Phase 7.

## Phase renumbering — 2026-09-10

Two capabilities that were never given a phase turned out to be prerequisites rather than nice-to-haves, and both are **platform** work rather than any one app's:

1. **Onboarding is all-or-nothing and unresumable.** After `register`, a user lands on the app chooser with no suite-level orientation. Picking LedgerCore hard-redirects to a wizard that cannot be skipped and holds its state in local component state — close the tab at step 2 and you start over. Nothing records that onboarding was ever begun.
2. **There is no way in for an existing business.** LedgerCore assumes an organization starts from zero on `books_start_date`. A business moving off QuickBooks, Xero or Tally arrives with a chart of accounts and a trial balance, and no route accepts either. `register` seeds a fixed default chart and that is the only chart obtainable without creating accounts one at a time.
3. **No file has ever been stored.** Phase 6 deliberately dodged this — a bank CSV arrives as a JSON string under `MAX_CSV_CHARS`, with a comment in three places deferring storage to Phase 10. But documents are a *suite* concern: LedgerCore wants a PDF on an invoice, AP-Flow wants the source image, BoardDeck wants the generated deck. Leaving storage inside AP-Flow would make every other app read AP-Flow's tables, which rule 16 forbids.

**QuickBooks sync is deferred, not dropped.** It has no dependents — nothing in the roadmap is gated on it — so it yields its number and moves to the tail rather than forcing a cascade:

| Was | Is now | Note |
|---|---|---|
| 9 — LedgerCore QuickBooks sync | **17** | Deferred. No phase is gated on it, so moving it costs nothing but its position |
| — | **9** (new) | Platform — onboarding & data migration |
| — | **9.5** (new) | Platform — the Document Vault |
| 10–16 | **unchanged** | AP-Flow, FP&A Engine, ForecasterPro, UnitEcon, BoardDeck, TaxGuard AI all keep their numbers |

**Why 9.5 rather than 10, and why it is a table row.** Making the Document Vault a whole number would push AP-Flow to 11–12 and cascade every phase below it, for the second time in ten days. The half-step precedent set by 3.5–3.9 exists precisely to add work without renumbering, and 9.5 sits immediately before Phase 10, which is its first consumer. It does deviate from that precedent in one respect, stated openly: 3.5–3.9 were discovered mid-build and appear only as delivered sections, never as table rows, whereas 9.5 is planned in advance and so takes a row like any other unstarted phase.

**Two settled rulings are amended by this entry.** Both were written down as decided, so both are reversed in the open rather than quietly:

1. **`multer` moves from Phase 10 to Phase 9.5.** [development.md](development.md)'s approved-dependency table assigns it to "AP-Flow's multipart document upload." The upload route is now platform-level, so the dependency lands with it. The rule itself is unchanged: no dependency before the phase that needs it. No storage SDK is approved by this entry — the filesystem backend stands, and MIME sniffing is hand-rolled in `utils/mimeSniff.ts` rather than taking `file-type`, matching how `utils/csv.ts`, `utils/levenshtein.ts` and `utils/dateParse.ts` were each built rather than installed.
2. **Document storage is no longer AP-Flow-owned.** The [Cross-cutting infrastructure](#cross-cutting-infrastructure) entry below assigned hash-addressed storage under `server/storage/` to Phase 10. Three apps now consume it, so it becomes shared infrastructure — `services/storageService.ts` and `services/documentService.ts` at the services-layer root, unprefixed, the same status as `authService`. This is the identical promotion `redactionService.ts` received in the [2026-09-01 entry](#phase-renumbering--2026-09-01), for the identical reason. It does not violate rule 16: `documents` is a platform table, so an app attaching a file talks to the platform, never to another app.

One design change comes with the promotion. AP-Flow's spec called for globally content-addressed storage — the filename *is* the SHA-256. Made suite-wide, that would let one tenant detect that another holds an identical file, and it would make deleting a blob unsafe whenever two organizations share it. The vault keys storage by organization instead (`server/storage/<org_id>/<ab>/<cd>/<sha256>`): two tenants uploading identical bytes get two blobs. It costs disk and buys tenant isolation, which is the trade this codebase makes everywhere else.

## Phase 9, as delivered

**9a — resumable, skippable onboarding.** A platform table `onboarding_states`, one row per `(org_id, app_slug)`, holding a four-state FSM (`NOT_STARTED → IN_PROGRESS → SKIPPED → COMPLETED`, with `COMPLETED` deliberately **not** terminal — re-running onboarding is already legal, since `completeOnboarding` is an upsert), the current step, and a `JSONB` draft. `app_slug` gets a non-blank CHECK and is validated against `isOnboardingSlug` (`isAppSlug` plus a `'platform'` sentinel) in the service rather than duplicating `config/apps.ts` into a database constraint — the same call migration 017 made for `audit_logs`. The draft is untrusted JSON: never spread into a query, always re-parsed through the target app's own zod schema at completion — see [study/typescript/runtime-validation-and-zod.md](../study/typescript/runtime-validation-and-zod.md).

`/api/v1/onboarding` is platform-level, not namespaced under `/ledger-core` (rule 16), mirroring `/audit-logs` and `/webhooks`: a checklist read, a draft autosave, skip, and resume. LedgerCore's existing `POST /settings/onboarding` stays the completer and marks its own row `COMPLETED` on the transaction it already owns (`onboardingService.markCompletedOnClient`, which runs no transition check at all — completion is legal from every state). Client-side, LedgerCore's route gate becomes **soft** — a skipped wizard leaves every route reachable behind a persistent `OnboardingBanner` instead of a forced redirect; `AppChooserPage` gains a `SetupChecklist` listing every `'building'` app's onboarding status. See [study/react/routing-nested-and-dynamic-segments.md](../study/react/routing-nested-and-dynamic-segments.md) for the hard-vs-soft gate distinction.

**A base-currency lock gap is closed here.** `PATCH /organizations` used to accept `baseCurrency` with no check that ledger lines exist — the lock lived only in the onboarding path. `organizationService.updateOrganization` now runs the identical guard (`422 Base currency cannot be changed once journal entries exist`) inside the same transaction as the write.

**9b — chart of accounts and opening balances.** Two staged importers, `CHART_OF_ACCOUNTS` and `OPENING_BALANCES`, reusing `utils/csv.ts` and `parseMoneyText` — no new dependency. **`utils/dateParse.ts` turned out not to be needed**: neither importer has a date column — a chart has no dates, and every opening balance posts at the single date `ledger_settings.books_start_date` — so this deviates from the original planned-scope wording below, recorded here rather than silently. **Deliberately shaped against Phase 6's bank import:** that one aborts the entire file on any bad row and writes live rows immediately. This one stages every row, good and bad, and separates validation from commit, because a partially-wrong chart is normal on a first export and re-uploading to discover the next error one at a time is a bad workflow. A `DRAFT → VALIDATED → COMMITTED` FSM (`migration_imports.status`), per-row errors and per-row fixes (`migration_import_rows.status`/`errors`), then one all-or-nothing commit transaction. See [study/architecture/staged-import-and-two-phase-commit.md](../study/architecture/staged-import-and-two-phase-commit.md).

Chart commit matches on `code`: an unknown code is created (parents resolved by parent *code*, depth-first over repeated passes until every row resolves — the same technique `seedDefaultChart` uses, generalized to a mix of existing and newly-staged rows), a known code merges `name`/`description` only — never `code` or `type`, which `updateAccountSchema` already refuses — and a type conflict is a row error that must be resolved before commit. A new `accountService.createAccountOnClient` (mirroring `journalService.createEntryOnClient`) lets the commit create every account inside its own transaction. Unused seeded accounts can be deactivated, never deleted; there is no account `DELETE` and the FKs forbid it.

Opening balances post **one** journal entry through `journalService.createEntryOnClient`, dated `ledger_settings.books_start_date`, with `source_type = 'opening_balance'` — never a direct `ledger_lines` write, so the period guard and the balance triggers apply unchanged. A partial unique index (`ux_migration_imports_one_committed_opening`) allows exactly one committed opening-balance import per organization, ever; a wrong one is corrected by a reversing entry (rule 6), never by re-importing. See [study/postgresql/partial-unique-indexes.md](../study/postgresql/partial-unique-indexes.md).

Three refusals define the accounting, and each closes a way the books could quietly start out lying:

- **Any imbalance is plugged to a new `3400 Opening Balance Equity` account**, shown in the preview before commit, never applied silently. A migration adds it to the default chart and backfills every existing organization, modelled on migration 003 — **the default chart becomes 45 accounts.**
- **`3200 Retained Earnings` is refused.** `reportService.balanceSheet` derives retained earnings and its own comment already warns that anything posted there is counted twice. An imported prior-year profit goes to `3400`, where it is a real posted equity balance and derived retained earnings correctly stays zero.
- **The AR/AP control accounts are refused.** A lump receivable with no invoices behind it would make `/reports/ar-aging`'s `reconciles` permanently `false`, and that flag is documented as a *correctness* claim about the books, not a completeness one. Open items migrate through the normal invoice and bill routes, which builds the control balance the honest way.

All five account types are accepted, so a mid-year migration can carry year-to-date revenue and expense; dated inside the current fiscal year, those land in the P&L and leave derived retained earnings at zero, which is right.

**`/api/v1/onboarding`** (5 routes) and **`/api/v1/migration-imports`** (9 routes: stage, list, get, list rows, patch a row, re-validate, preview, `OWNER`/`ADMIN`-only commit, delete). Full detail: [api.md](api.md). **Client:** `OnboardingBanner`, `SetupChecklist` (on `AppChooserPage`), a `Skip for now` button and draft autosave on `OnboardingPage`; `MigrationImportsPage` (register), `NewMigrationImportPage`, `MigrationImportDetailPage` (staged rows, inline fixes, the commit preview, `ConfirmDialog`-gated commit and delete), a new Data migration sidebar group.

**Acceptance ✅ — verified.** A chart CSV with two deliberately corrupt rows stages the rest as `VALID` and commits only after both are fixed (`chartImport.test.ts`). An unbalanced trial balance imports, commits with the difference in `3400`, and `GET /reports/balance-sheet` still balances by integer equality (`openingBalanceImport.test.ts`). A second committed opening-balance import is refused by the partial unique index itself, proven with raw SQL bypassing the service entirely (`migrationImportConstraints.test.ts`). **811 server tests** (up from 776) **+ 161 client tests** (up from 150), each new module carrying its own cross-tenant isolation case.

**Deliberately not built:** open-item (per-customer, per-vendor) import; foreign-currency opening balances — a foreign balance needs a frozen rate on a document that does not exist yet; API-based migration from QuickBooks or Xero, which is Phase 17's shape rather than this one's; undo of a committed import beyond the reversing entry; whole-chart account-code remapping; a database-level immutability trigger on a `COMMITTED` `migration_imports`/`migration_import_rows` row (the service refuses every write once `COMMITTED`, but nothing yet stops a raw `UPDATE` the way `invoices`/`bills`/`payments` are stopped — see [schema.md](schema.md#phase-9b--chart--opening-balance-import-ledgercore--applied)); a suite-level onboarding wizard UI for the `'platform'` sentinel (the row exists and is tracked, but only LedgerCore's app-level wizard has a page).

## Phase 9.5, as delivered

**Built in full**, 2026-09-10. A half-step: it renumbers nothing. Phase 10 followed the same day — see [Phase 10, as delivered](#phase-10-as-delivered) below.

A platform `documents` table — SHA-256, byte size, sniffed MIME type, original filename, `UNIQUE (org_id, sha256)` so re-uploading a file is idempotent — plus `document_links`, keyed by `(org_id, document_id, app_slug, entity_type, entity_id)`. That link table is what keeps rule 16 intact: LedgerCore attaching a PDF to an invoice and AP-Flow attaching a source image are both apps talking to the platform, never to each other.

`services/storageService.ts` keeps the narrow interface [architecture.md](architecture.md#target-layout) already reserved for it — `put`, `get`, `stat` — so object storage stays a one-file swap. Paths are org-scoped and two-level hex fanned-out, for the isolation reason given in the [renumbering entry](#phase-renumbering--2026-09-10) above.

`/api/v1/documents` is platform-level: upload, list filtered by app and entity, metadata, a streamed download, attach and detach, and a delete that is refused while any link exists. Upload takes `multer` in **memory** storage with a hard size cap, decides the MIME type by **magic bytes and never by the client's `Content-Type` header** (`utils/mimeSniff.ts`, hand-written — no `file-type` dependency), allowlists PDF/PNG/JPEG/CSV, and hashes with `node:crypto`. Downloads set `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`. The blob is written before the database row, and an orphaned blob is tolerated on rollback — rule 5 forbids post-`COMMIT` follow-up work, and an unreferenced file is inert.

**Two deliberate deviations from this section's original planned wording**, recorded here rather than silently, the same way Phase 9b recorded `dateParse` going unused:

1. **`documents` is update-immutable by trigger, not "insert-only.**" `DELETE /documents/:id` is a real route — a document can be removed once nothing links to it, refused with `409` by `documentService` while any `document_links` row still references it. Only `UPDATE` is rejected by the database (`reject_document_mutation()`, raising `0A000`). "Insert-only" was the earlier wording ([schema.md](schema.md) originally said this too, corrected in the same pass); "update-immutable, deletable while unlinked" is what actually shipped.
2. **`documents`/`document_links` carry `created_at` only, no `updated_at`.** Neither row is ever updated, so a `set_updated_at` trigger would have nothing to do.

On the client the vault is a suite-level destination beside `/account`, plus a reusable attachments panel (`components/AttachmentsPanel.tsx`) dropped onto LedgerCore's invoice, bill and journal-entry detail pages — the cross-app proof that the service is genuinely platform-level rather than LedgerCore's with a different prefix.

**Acceptance ✅ — verified.** A PDF renamed with a `.csv` extension is still sniffed as `application/pdf` from its magic bytes, never trusted by filename (`mimeSniff.test.ts`). Two organizations uploading byte-identical files receive two distinct documents at two distinct storage paths (`storageService.test.ts`). A cross-tenant `GET`/`GET .../file`/`DELETE` against another organization's document id returns `404`, never `403` (`platform/documents.test.ts`). The composite FK rejects a `document_links` row whose `org_id` doesn't match its document's, proven with raw SQL bypassing the service entirely, alongside the `0A000` immutability check on both tables (`platform/documentConstraints.test.ts`). **868 server tests** (up from 811) **+ 172 client tests** (up from 161).

**Deliberately not built:** object storage; virus scanning; thumbnail or preview generation; document versioning; blob garbage collection; per-document permissions finer than organization membership; a storage-integrity check comparing `documents` rows against blobs actually on disk (`verify:integrity` does not cover this).

## Phase 10, as delivered

**Built in full**, 2026-09-10. `config/apps.ts` flips `ap-flow` from `'planned'` to `'building'`. Produces a draft extraction; **posts nothing to the ledger** — that stays Phase 11's, along with COA mapping, tax split, FX-at-invoice-date, and the review queue.

Four dependencies, all pre-approved for this phase: `tesseract.js` (local OCR — local is the point, PII is located and masked before any image leaves the machine), `sharp` (rasterizing and masking image buffers), `pdfjs-dist` (rendering PDF pages to images), `@anthropic-ai/sdk` (vision extraction of the already-redacted image). `@napi-rs/canvas` appears in the lockfile as `pdfjs-dist`'s own transitive `optionalDependency` — never a direct dependency here, never imported directly; `pdfjs-dist` auto-selects it as its Node canvas factory.

Migration 031: `ap_flow_documents` (registers a platform vault document for processing, a four-state status with **no terminal state** — the first FSM in this codebase where that's true, because nothing here has posted to the ledger yet), `ap_flow_pages` (rasterized/redacted page metadata — one more table than the phase's original sketch), `ap_flow_extractions` (one current extraction per document, replaced wholesale on re-extraction rather than appended). `ap_flow_pages` is deliberately unaudited, the same ruling `bank_match_suggestions` got in migration 019.

The pipeline (`queue/handlers/apFlowExtractHandler.ts`, running as an `ap-flow-extract` background job — event-driven, no repeat schedule) is strictly ordered: rasterize → local OCR → detect PII (hand-written Luhn/Verhoeff checksums, not digit-count matching) → mask (destructive pixel compositing, never a recoverable overlay) → **only then** vision extraction, on the redacted bytes alone. `redactionService.ts` is unprefixed, shared infrastructure, matching `docs/capture.md`'s own promotion note. Every real I/O boundary (`OcrAdapter`, `VisionClient`) is injectable, which is what makes the whole pipeline testable with zero network calls in CI.

Vision extraction forces a tool call (`record_invoice`) rather than parsing free-form text, so a malformed response is structurally impossible; money crosses that boundary as decimal strings, never JSON numbers, so a model's answer never touches a float on its way to becoming cents. An arithmetic contradiction (line items vs. subtotal, subtotal+tax vs. total) is **flagged**, never silently accepted and never auto-rejected — Phase 10 posts nothing, so there's nothing yet to protect by refusing outright.

`/api/v1/capture/documents` — 5 routes (register, list, get, redacted page image, re-extract) — platform-app-namespaced under `/ap-flow`, `org_id` still the only tenancy boundary underneath. Client: `ApFlowDocumentsPage` (a capture control reading the vault's own document list, filtered client-side to scannable MIME types), `ApFlowDocumentDetailPage` (the redacted preview image captioned as exactly that, extracted fields with per-field confidence, an arithmetic-warning panel, `Re-extract` gated by `ConfirmDialog`) — deliberately thin, no per-field editing or account override, which are Phase 11's.

**Three deliberate deviations from this phase's original planned shape**, recorded here rather than silently:

1. **A third table, `ap_flow_pages`, beyond the two the ladder named.** Redacted-page metadata (dimensions, the redacted image's own hash, the masked regions) didn't fit cleanly on either `ap_flow_documents` or `ap_flow_extractions` without conflating "one document" with "one page" — a multi-page PDF needs its own row per page.
2. **The registration enqueue sits outside its own database transaction**, deliberately — a Postgres commit and a Redis `enqueue()` are two separate systems, and enqueuing *inside* the transaction would risk firing a job for a row a subsequent rollback then erases. The accepted cost is the opposite, narrower gap: a crash between commit and enqueue leaves a document visibly stuck at `PENDING`, recoverable via `POST /:id/reextract`. This is **not** routed through the transactional outbox (Phase 7) — that mechanism exists for financial events where losing one silently is unacceptable, and nothing here is financial yet.
3. **The acceptance test proves masking with a generated fixture and an injected fake OCR adapter, not real tesseract.** A hermetic CI run and a real-OCR assertion can't both be satisfied without vendoring a 15MB language pack into the repo. Detection (`pii.test.ts`) and masking (`redaction.test.ts`) are each proven directly, and a real-`tesseractOcr` case exists gated behind `AP_FLOW_OCR_E2E=1`, run deliberately rather than automatically.

One promotion, client-side, recorded the same way: `BackLink.tsx`, `ConfirmDialog.tsx` and `money.ts` moved from `Pages/` to `components/`/`utils/` — AP-Flow's pages needed all three, and an app importing from another app's page directory would be the client mirror of a rule-16 violation. The same move `redactionService.ts`/`storageService.ts` got on the server, for the identical reason: a third consumer makes a file shared infrastructure.

**Acceptance ✅ — verified.** A generated fixture image's masked region reads `(0,0,0)` at every pixel after `redactPage`, while at least one of those same pixels was demonstrably not black before — a raw-pixel comparison, not "the code ran without throwing" (`redaction.test.ts`). A stubbed vision client's captured input bytes hash-match the bytes stored at `redacted_sha256` and do **not** match the rasterized original (`pipeline.test.ts`) — the acceptance criterion for the phase's headline claim. A non-Luhn 16-digit run is left unmasked; a Luhn-valid one is masked across every OCR word it spans (`pii.test.ts`, `redaction.test.ts`). Cross-tenant isolation holds at both the API (`ap-flow/documents.test.ts`) and the worker (`pipeline.test.ts`, a handler run with the wrong `orgId` touches nothing). The database — not the service — rejects an in-place edit of a redacted page or an extraction, and a cross-tenant `ap_flow_documents` registration, proven with raw SQL bypassing `captureDocumentService` entirely (`apFlowConstraints.test.ts`). No test in the suite makes a network call or needs `ANTHROPIC_API_KEY`. **932 server tests** (up from 868) **+ 1 gated E2E case reporting as skipped** **+ 181 client tests** (up from 172).

**Deliberately not built:** posting to the GL; COA mapping from vendor history; tax split; FX normalization at invoice date; the human review queue UI; `ap_flow_line_items` as a real table (line items stay JSONB on `ap_flow_extractions` until Phase 11); a measured PII-detection recall figure, and therefore no "PII cannot leak" claim — the honest claim is "redaction pipeline implemented" (see [study/security-auth/pii-detection-and-redaction.md](../study/security-auth/pii-detection-and-redaction.md)); handwriting or non-English OCR; multi-document PDF splitting; duplicate-invoice detection; re-extraction history (a re-extract replaces the prior attempt; only `audit_logs` remembers it existed).

## Phase 11, as delivered

**Built in full**, 2026-09-11. AP-Flow's own draft finally reaches the ledger — the last piece the roadmap owed it. Zero new dependencies.

Migration 032 widens `ap_flow_documents.status`'s CHECK to add **`POSTED`** — this table's first terminal state, replacing the "nothing here is terminal" ruling Phase 10 recorded. `EXTRACTED → POSTED` is the only inbound edge; `POSTED`'s own edge list is empty, enforced twice — once in `AP_FLOW_DOCUMENT_TRANSITIONS`, once by `trg_ap_flow_documents_posted_guard`, a `BEFORE UPDATE` trigger with no carve-out at all (unlike `invoices`' `ISSUED → VOID` exception). Two new tables: `ap_flow_line_items` (materializing what was JSONB-only on `ap_flow_extractions.line_items`, mutable until its parent document posts, then frozen by `trg_ap_flow_line_items_posted_guard` reading the parent's own status) and `ap_flow_vendor_account_map` (the organization's own posting history, keyed by a normalized vendor-name string it computes itself, never LedgerCore's `vendors.id`). Both new tables are audited, unlike `ap_flow_pages` — a reviewer's override and a posting's vendor-history write are business state, not derived output.

**One deliberate scope correction against this doc's own build ladder, made before writing any code:** the ladder's "tax split into `1180` / `2140`" is wrong on its own terms — the two paragraphs above it in [capture.md](capture.md) already say input tax on a *purchase* is an asset (a claim against the tax authority), and `2140 GST/VAT Output Payable` is the *sales* side, which AP-Flow never touches. Posting debits only `1180`; no AP-Flow code path writes `2140`, proven in `posting.test.ts`. **A second correction:** this table's own Phase 11 row and `config/apps.ts`'s AP-Flow skills list both named "3-way matching" and "COGS tracking," neither of which appears in [capture.md](capture.md)'s Phase 11 ladder or acceptance criteria — the detailed spec is authoritative per this table's own note, so neither was built, and both strings are corrected below and in `config/apps.ts`.

**Classification runs as three tiers, cheapest first, each skipping the rest once it hits:** (1) history — an exact `ap_flow_vendor_account_map` lookup, winning outright with no downstream tier ever called; (2) chart — Levenshtein similarity (`utils/levenshtein.ts`, already built for Phase 6) between the line description and every postable Expense account's name, threshold `0.62`, tuned by hand against the default chart and **not measured against a labelled corpus**; (3) the model, given only the still-unmapped lines and the chart's own codes, forced into a `suggest_accounts` tool call so a code outside the chart is structurally discarded rather than becoming a suggestion. Tier 3 is the one place in this pipeline that degrades instead of failing: a missing `ANTHROPIC_API_KEY` or a thrown error leaves those lines `mappingSource: 'NONE'` and logs a warning — the extraction already succeeded, and a classification miss is a reviewer's problem, not a re-run.

**Posting (`services/capture/postingService.ts`) is the app boundary in practice**, and the diff proves it structurally: `grep -rnE "FROM (accounts|journal_entries|ledger_lines|ledger_settings|fx_rates)\b" server/src/services/capture/ server/src/controllers/capture/ server/src/routes/capture/` returns nothing. Every LedgerCore fact — the chart, the posting accounts, the exchange rate — arrives through an exported LedgerCore service function (`accountService`, the newly-promoted `settingsService.resolveApPostingAccountsOnClient`, `fxRateService.requireRateOnClient`) called on this file's own checked-out transaction client, and the entry itself is created by `journalService.createEntryOnClient` with `source_type = 'ap_flow'`, `source_id` = the AP-Flow document's own id. One transaction: the FSM lock, every refusal check, the FX resolution, the posting, freezing `journal_entry_id`/`posted_sha256`/`posted_at`/`posted_by` on the AP-Flow row, and the vendor-history upsert all commit together or not at all — no work after `COMMIT`.

**FX resolves at the invoice date**, never the posting date — AP-Flow has only the one date, unlike a bill's separate `bill_date`/posting-date split. **The expense debit is the line items' own summed amount, never `subtotal_cents`** — a reviewer's account override changes which account is debited, never how much, and a pre-flight integer-equality check (`422`, not a `500` — a bad number here is untrusted model output, not a service bug) refuses to post if line items plus tax don't sum to the total. Two line items on the same account merge into one ledger line, exactly like `billService.approveBill`'s expense-account grouping.

`journal_entry_id` and `ap_flow_line_items.account_id`/`ap_flow_vendor_account_map.account_id` carry **no `REFERENCES`** — rules 8 and 16 collide, and 16 wins, the same ruling `journal_entries.source_id` and `document_links.entity_id` already carry. Validity is enforced at the service layer three times over, ending at `journalService.createEntryOnClient`'s own postable-account check inside the posting transaction.

`GET /ap-flow/review-queue` orders documents arithmetic-failure first, then any unmapped line, then lowest model confidence, then newest — a `LATERAL` join computing `min()` over `jsonb_each_text(field_confidence)` and a count/count-filter pair over `ap_flow_line_items`, both scoped inside the lateral rather than the outer `WHERE`. `PATCH /documents/:id/line-items/:lineId` validates its account through `accountService.getAccountById` (`404` cross-tenant, `422` for a header or inactive account) and sets `mappingSource: 'MANUAL'`. `POST /documents/:id/post` takes no request body — there is nothing for a caller to supply, and accepting one would let a client forge provenance.

Client: `ApFlowReviewQueuePage` (the queue, confidence colour-banded red/amber/neutral), `ApFlowDocumentDetailPage` restructured into a two-column review — the existing redacted-preview caption unchanged, a per-line account `<select>` beside a mapping-source chip, and a `ConfirmDialog`-gated **Post to ledger** button disabled with a stated reason whenever arithmetic fails or a line is unmapped. A `POSTED` document shows its journal-entry link, posting timestamp, and `posted_sha256` in a labelled `font-mono` block, with Post and Re-extract both absent rather than disabled.

**Acceptance ✅ — verified**, the phase's own three criteria, each a named test in `posting.test.ts`: a two-line receipt posts one balanced entry debiting two different accounts (`a two-line receipt posts one balanced entry debiting two different accounts`); re-approving a posted document returns `409` and creates no second `journal_entries` row (`re-posting the same document does not create a second entry`); the posted entry's `source_id` resolves back to a document whose `posted_sha256` still matches the bytes in the vault (`the posted entry's source_id resolves back to the document's stored hash`). `npm run verify:integrity` passes after AP-Flow has posted. Cross-tenant isolation and the ROLLBACK path (a failed post leaves the document `EXTRACTED` and `ledger_lines` row count unchanged) are both proven. **984 server tests** (up from 932, plus the same 1 gated E2E case still reporting as skipped) **+ 189 client tests** (up from 181).

**Deliberately not built, per this doc's own scope correction above:** 3-way matching; COGS tracking; a `2140` write path anywhere in AP-Flow. Also not built: editing an extracted amount (only the account per line is editable — a wrong number is fixed by re-extracting); un-posting or reversing from AP-Flow's own side (correction is LedgerCore's `POST /journals/:id/reverse`, reached from the linked journal entry); an outbox event or webhook for a posting (the five events CLAUDE.md names are the complete set; nothing here adds a sixth); open-item or partial-document posting; duplicate-invoice detection; a measured PII-detection recall figure, unchanged from Phase 10's own limit.

## Module map

The domain, headline skills, and DB/engineering pattern for each module of the product. Headings keep each module's original app name alongside its current one (Phase 33).

### Accounting (was LedgerCore) — Core Accounting & Systems — Phases 3–4, 6, 8, 9b, 17

The system of record every other app posts into. Double-entry integrity enforced by the database itself, an append-only ledger, multi-currency, bank reconciliation, and a QuickBooks API sync. Full spec: [accounting.md](accounting.md).

*Includes:* chart of accounts with parent/child hierarchy, manual journal entries, reversing entries, trial balance, fiscal periods with close/lock, P&L, balance sheet, AR/AP subledgers, bank CSV ingestion with confidence matching, multi-currency FX with realized and unrealized gain/loss, chart and opening-balance import for a business migrating in (9b), QuickBooks Online sync (17).

*Pattern:* strict double-entry validation inside `BEGIN...COMMIT`, all amounts integer cents, and the same invariant enforced a second time by a `DEFERRABLE INITIALLY DEFERRED` constraint trigger that fires at `COMMIT` — the application is not the only thing standing between the ledger and an unbalanced entry. Posted rows are immutable by trigger, not by convention. `source_type` / `source_id` on `journal_entries` is the hook every other app uses to post into the GL.

### Capture — the bill inbox (was AP-Flow) — Operational Accounting — Phases 10–11, 19

A photograph of a receipt becomes a balanced, auditable journal entry. Full spec: [capture.md](capture.md).

*Pattern:* documents are OCR'd **locally** first, so PII can be located and masked on the pixels before any image reaches an external vision model; the redacted image then goes to Claude Vision for structured extraction with per-field confidence. GL coding is inferred from the organization's own posting history before a model is consulted. Individual line items map to distinct accounts, not one lump total. Posts into LedgerCore via `source_type = 'ap_flow'`, stamping the source document's SHA-256 onto the entry so an auditor can walk from a ledger line back to the original image.

### Inventory (was StockLedger) — Inventory & Warehousing — Phases 28, 32

Perpetual inventory for retail traders, manufacturers, distributors and real-estate developers alike. Full spec: [inventory.md](inventory.md).

*Pattern:* an industry-chosen starting catalogue (10 profiles, code copied into the org's own tables, not read live); per-org custom item/serial attributes as JSONB, validated in the service layer against a relational definitions table; a configurable item-code grammar with per-scope-key gapless counters; QR label generation with a deliberately minimal scan payload; moving-average and specific-identification perpetual valuation over an append-only movement ledger with an integrity-checked derived balance cache; deterministic multi-row lock ordering to keep concurrent transfers deadlock-free. `requires: []` — the one app in the suite posting nothing to the GL and reading no other app's tables; the eighth app added to the registry, not a LedgerCore module — Phase 29 later retired five of the other seven.

**Five further apps once had their own entry here** — TaxGuard AI (Phase 16, RAG over `pgvector` with question redaction), FP&A Engine (Phase 12, a linked 3-statement projection model), ForecasterPro (Phase 13, driver-based rolling forecasts and zero-based budgeting), UnitEcon (Phase 14, cohort retention and PVM variance), and BoardDeck Automator (Phase 15, close automation and `.pptx` deck generation) — all removed from the suite on 2026-09-23. See [Phase 29, as delivered](#phase-29-as-delivered) for what was removed and why, and their now-deleted spec files' last content in git history if the mechanism detail is needed.

**Built 2026-09-13/14.** AP-Flow's straight-through-processing slice: a second extraction/classification provider, posting rewritten onto a real LedgerCore bill, a confidence-gated auto-post, and direct upload from AP-Flow's own page. A gated live case (`AP_FLOW_GEMINI_E2E=1`) proves a real Gemini call end to end; every other case in the suite injects a stub and makes zero network calls, matching Phase 10's own discipline.

**Amendment, 2026-09-14 — the shipped default Gemini model was retired.** `gemini-2.5-flash`, the default `CAPTURE_GEMINI_MODEL` at ship time, began returning `404` ("no longer available to new users") for this project's key — it still appeared in Google's `ListModels`, but `generateContent` had stopped serving it. Fixed by pinning the default to `gemini-3.6-flash` and adding a new `geminiThinkingConfig` export to `modelClient.ts`: Gemini 3.x replaced the 2.5 family's `thinkingConfig.thinkingBudget` (an integer token allowance) with `thinkingConfig.thinkingLevel` (a coarse enum), and some 3.x models — `gemini-3.6-flash` confirmed — hard-reject the old `thinkingBudget` field with `400 INVALID_ARGUMENT` rather than ignoring it, so the fix is model-family-aware rather than a blanket swap: `gemini-2.5-*` still gets `thinkingBudget: 0`, everything else gets `thinkingLevel: 'low'`. The gated E2E case (`AP_FLOW_GEMINI_E2E=1`) is what proved the live path end to end — and turned up a second, unrelated pre-existing bug in the same file: the suite-wide `beforeEach` stubbed `globalThis.fetch` to throw for every case, including the live one, so that case had never actually reached the network even when force-enabled; fixed by restoring the real `fetch` at the top of that one case. The Gemini 502 error message (`"Gemini request failed with status <code>"`) now also appends Google's error `status` enum in parentheses when present (e.g. `(NOT_FOUND)`) — never the provider's free-text message — so a future retirement is diagnosable from the failed document's `failure_reason` alone, without needing live API probing to identify. A full, unmocked `npm test` run (not done routinely — it takes ~30 minutes against real Postgres) turned up a third, unrelated pre-existing gap in the same incident: `vitest.config.ts`'s test `env` override never pinned `CAPTURE_AI_PROVIDER`/`ANTHROPIC_API_KEY`/`GEMINI_API_KEY`, so with a real `CAPTURE_AI_PROVIDER=gemini` and a live key already in this project's `server/.env`, two tests that assert the *unconfigured*-provider fallback (`extraction.test.ts`'s `503`, `mapping.test.ts`'s `NONE`) were silently making real calls to a real model instead. Fixed by pinning those three variables to the unconfigured state in `vitest.config.ts`, matching the file's own stated intent that the suite "does not depend on what happens to be in your local `.env`." Confirmed with two full suite runs: 116/116 files, 1455 passed, 2 skipped (the gated live cases), 0 failed.

**Tax allocation and vendor resolution.** `utils/money.ts` gained `allocateCents` — largest-remainder allocation in exact `BigInt` arithmetic, guaranteeing the parts sum to exactly the input total, which per-line `scaleCents` cannot promise. `vendorService.findOrCreateVendorByNameOnClient` matches an existing active vendor by normalized name or creates one, serialized per `(org, normalized name)` by a transaction-scoped `pg_advisory_xact_lock` against the race a plain `SELECT`-then-`INSERT` would leave open (`vendors.name` carries no `UNIQUE` constraint). Posting a duplicate invoice number for a vendor is now a clean `409`, for free, via `ux_bills_vendor_reference` — duplicate-invoice detection nobody had to build separately.

**Confidence-gated auto-post.** Off by default, per organization (`ap_flow_settings`, migration 050). `services/capture/autoPostPolicy.ts`'s `evaluateAutoPost` is pure — no database, no network — and checks every gate rather than stopping at the first failure (arithmetic, vendor name, invoice number, invoice date, positive total, line items present and mapped and non-negative, field/mapping confidence against the configured threshold, an optional base-currency amount limit), so a reviewer sees the complete picture in `auto_post_blockers` in one read. `HISTORY`-tier account mappings bypass the confidence threshold — an organization's own posting history is ground truth, the identical ruling Phase 11 gave it at classification time. The extraction worker calls `attemptAutoPost` directly after `savePipelineResult`; it never throws, so a blocked or rejected auto-post (a duplicate invoice, a locked fiscal period, a missing FX rate) degrades to a recorded `POSTING_REJECTED` blocker rather than ever marking a cleanly-extracted document `FAILED`.

**Direct upload (`POST /ap-flow/documents/upload`).** Vaults and registers a document in one call — `ApFlowUploadPanel.tsx` on `ApFlowDocumentsPage` — rather than requiring the vault's own upload page first. Also fixed, incidentally: the documents list previously rendered a `POSTED` document with the `Failed` pill (the `StatusPill` component had never been given a `POSTED` branch).

## Phase 19.1, as delivered

**Built 2026-09-17.** A platform-level `ai_model_calls` table (migration 051) and `services/aiUsageService.ts` — every AP-Flow extraction/classification call is recorded with its token counts, latency, outcome, and cost when the calling model carries a verified price, surfaced over `GET /api/v1/ai-usage` and on each document's own detail page. No new dependency, server or client — token usage is read straight off the provider responses `modelClient.ts` already parses.

**A real gap in the existing seam, found and fixed as a prerequisite.** `StructuredModelClient.generateStructured` returned only the model's structured output — every token count both Anthropic and Gemini already send back was being silently discarded. `generateStructured` now returns `{ value, usage }`; `normalizeAnthropicUsage` and `normalizeGeminiUsage` (both new exports on `modelClient.ts`) fold each provider's incompatible usage shape into one `ModelUsage` type. Anthropic's `cache_creation_input_tokens` (a cache **write**, billed as input) is folded into `inputTokens`; `cache_read_input_tokens` is reported separately as `cachedInputTokens`. Gemini's `thoughtsTokenCount` is billed as output, so it is folded into `outputTokens` **and** reported separately as `reasoningTokens` for visibility — `reasoningTokens` is informational only and is never added to a cost a second time.

**Costing.** `utils/microUsd.ts` is operational AI spend in millionths of one US dollar — its own branded integer type, deliberately never `Cents` and never in `utils/money.ts`: a single model call routinely costs a fraction of one cent, which cents cannot represent, and a separate brand makes "AI spend posted to the GL" a compile error rather than a rounding argument. `config/aiPricing.ts` holds one hand-verified price (`claude-sonnet-5`: $2.00/$10.00 per 1M input/output tokens, verified against Anthropic's published table 2026-06-24) under a version stamp, `AI_PRICING_VERSION`. A model absent from that table — Gemini, at ship time, since its price was not verified when this table was written — is not an error: its calls are recorded with real tokens and `cost_micro_usd NULL`, and the usage summary reports them separately as `unpricedCallCount` rather than folding a fabricated number into the total. The AI usage page states this explicitly rather than showing a total that silently understates real spend.

**Recording seam.** `extractionService.ts` and `mappingService.ts` must never import `db/connect.js` (both files' own header comments say so). Metering is reported instead through an injected `onModelCall` callback — `queue/handlers/apFlowExtractHandler.ts` builds one closure per pipeline run and passes it into both services, filling in `entityType`/`entityId`/`createdBy` the services themselves don't know. `aiUsageService.recordCall` never throws — a metering failure is logged and swallowed, the same posture `autoPostService.recordBlockersSafely` already takes, because a spend-tracking bug must not be able to fail a document that extracted fine. Only calls that actually reached a provider are recorded — a `503 "... is not configured"` throws before any request and records nothing.

**Schema.** `ai_model_calls` (migration 051) is a **platform** table, not namespaced under AP-Flow — `app_slug` on the row carries the namespace, the identical convention `audit_logs`/`document_links` already use (rule 16), so TaxGuard AI can adopt this table later with zero migration. Append-only by a `BEFORE UPDATE`-only trigger (never `BEFORE DELETE`, so an org's cascade-delete still works); deliberately not CDC-audited, since it admits no UPDATE/DELETE for `audit_row_change` to capture and doing so would only duplicate every INSERT into a second append-only table at the same volume.

**Client.** A new `ApFlowUsagePage.tsx` (`/app/ap-flow/usage`) with date-range filtering, totals, and by-model/by-purpose/by-day tables; a per-document "AI usage for this document" panel on `ApFlowDocumentDetailPage.tsx`.

Full server and client suites pass, zero regressions in either pre-existing suite — see the combined count in [Phase 19.2, as delivered](#phase-192-as-delivered) below (both half-steps landed in the same pass and share one final verification run). Cross-tenant isolation proven: one organization's `GET /ai-usage` totals stay zero after another organization records calls, `listCallsForEntity` returns nothing for another organization's entity id, and a forged `orgId` in the query string, a header, and the body simultaneously is byte-identical to the honest response.

**Deliberately not built.** Retention or partitioning on `ai_model_calls` despite unbounded growth — the same accepted posture `audit_logs` already carries at portfolio scale. A verified cached-input pricing rate distinct from the plain input rate — harmless today since no AP-Flow caller sends `cache_control`, so `cached_input_tokens` is always `0`, but `aiUsageService`'s comment flags it as a real over-estimate the moment prompt caching is introduced. ## Phase 19.2, as delivered

**Superseded the same day by [Phase 19.3, as delivered](#phase-193-as-delivered) below** — kept here as history; the tables this section describes were renamed and the single-folder design replaced.

**Built 2026-09-17, the same pass as 19.1.** Google Drive folder intake — the item Phase 19 deferred, not dropped. A per-org OAuth 2.0 + PKCE Drive connection (`drive.readonly` scope), a background sweep polling every connected organization every 5 minutes, and a manual "Sync now". No new dependency: OAuth and the Drive v3 REST surface are hand-rolled over `fetch` (`services/capture/googleDriveClient.ts`) — no `googleapis` SDK, the identical no-SDK precedent `modelClient.ts`'s Gemini adapter and `embeddingService.ts`'s Voyage adapter already set; encryption and hashing come from Node's built-in `node:crypto` (`utils/secretBox.ts`, `utils/pkce.ts`), the same module `utils/webhookSignature.ts` already uses. Migration 052.

**This is the design `plans/phase-19-ap-flow-automated-intake.md`'s Slice E specified, re-verified against the tree on 2026-09-17 and executed with the corrections that drift required** — the migration number (051 was already taken by 19.1's metering table), a few "new" steps that turned out to already exist from Phase 19 itself (the settings page, its route, and the auto-post/settings client fetchers), and nothing else. The plan file has been deleted now that its design has shipped.

**OAuth flow.** `startConnect` generates a random `state` and PKCE `verifier`, stores only a SHA-256 hash of the state and an AES-256-GCM-encrypted verifier, and returns Google's authorization URL. `completeConnect` — reached at `GET /drive/oauth/callback`, which carries **no session** — claims the matching state row first (atomically clearing it, so it is single-use) and only then calls Google, with no transaction held open across that network call (rule 5). The org comes from the matched row, never from the request — the state hash *is* the credential, the first of two documented exceptions to rule 1 in this slice (the second is the scheduler's `listConnectionsDueForSync`, which reads across every organization by design, ids only, every downstream call re-scoping by that row's own `org_id`).

**Secrets at rest.** The refresh token and PKCE verifier are AES-256-GCM encrypted (`utils/secretBox.ts`, a random 12-byte IV per call, format `v1.<iv>.<tag>.<ciphertext>`) under `INTEGRATION_ENCRYPTION_KEY` — a separate concern from the JWT token secrets (rule 11), never reused. `GET /drive` never selects the ciphertext columns; no log line, error message, or API response in this slice ever includes a token, verifier, state, or ciphertext.

**Import pipeline.** A sync lists the connected folder's PDF/PNG/JPEG files, skips any Drive file id already seen for that organization (`ap_flow_drive_files`, `UNIQUE (org_id, drive_file_id)` — one file is imported at most once, even across a folder change or a reconnect), and imports up to `AP_FLOW_DRIVE_MAX_FILES_PER_SYNC` (25) new ones per run through the exact same `captureDocumentService.captureFile` path direct upload uses. An imported file is therefore extracted, classified, metered (19.1, for free — no extra wiring), and auto-posted if the organization has that enabled, indistinguishable from a file dropped in by hand. A file over the 10 MB limit is skipped without ever being downloaded (`Content-Length` checked before the body is read, then the actual byte count after). `invalid_grant` on a refresh (Google access was revoked) moves the connection to `NEEDS_REAUTH` rather than failing the sync loudly.

**Schema.** `ap_flow_drive_connections` (`UNIQUE (org_id)`, one connection per tenant) and `ap_flow_drive_files` (migration 052). `ap_flow_drive_files.ap_flow_document_id` uses PostgreSQL 15+'s column-list `ON DELETE SET NULL (ap_flow_document_id)` form — nulling only that column, never `org_id`, when the AP-Flow document it points at is deleted, avoiding the two-column composite-FK `SET NULL` trap that would otherwise corrupt tenant scoping on the surviving row (see [study/postgresql/composite-foreign-keys-for-tenancy.md](../study/postgresql/composite-foreign-keys-for-tenancy.md)). Neither table is CDC-audited — `audit_row_change` would copy `refresh_token_ciphertext` into an append-only `audit_logs` row forever, and an encrypted secret is still a secret.

**Client.** A "Google Drive" card added to the existing `ApFlowSettingsPage.tsx`, beside the Phase 19 auto-post card — connect/reconnect, folder input, sync-now, status, and a `ConfirmDialog`-gated disconnect that states plainly it removes only the connection, not files already imported.

**Acceptance ✅ — verified.** `npm run migrate` applies migrations 051 and 052 idempotently, twice, in the same run 19.1 verified. **1546 server tests** (up from 1451, +95 — the full suite, one clean run, zero regressions, 2 skipped: the pre-existing gated live-provider cases) **+ 257 client tests** (up from 247, +10). New server coverage: 16 metering unit tests (`microUsd.test.ts`), 6 secretBox/PKCE tests, 10 constraint tests (`platform/aiUsageConstraints.test.ts`), 17 service/route tests (`platform/aiUsage.test.ts`), 8 Google Drive client tests (`googleDriveClient.test.ts`), 16 Drive intake tests (`driveIntake.test.ts`), plus ~19 new cases folded into `modelClient.test.ts`/`extraction.test.ts`/`mapping.test.ts`/`pipeline.test.ts`/`apFlowConstraints.test.ts`. New client coverage: 6 `apFlowUsage.test.tsx`, 4 `apFlowSettings.test.tsx`. Cross-tenant isolation proven: a sync against another organization's connection id writes nothing to either organization's `ap_flow_documents`; `GET /drive` under a forged org header still returns only the honest org's own connection.

**Two real bugs found and fixed by the tests themselves, not by inspection.** `completeConnect`'s claim query set `pkce_verifier_ciphertext = NULL` and tried to `RETURNING` it in the same statement — `RETURNING` reflects post-update values, so the returned ciphertext was always `NULL` and every real OAuth completion would have failed decrypting it. Fixed by splitting the claim into a `SELECT ... FOR UPDATE` (captures the old value) followed by a separate `UPDATE` inside the same transaction, atomic via the row lock, and still satisfying `chk_ap_flow_drive_connections_state_complete`'s all-three-null-together invariant. Separately, `completeConnect`'s final `UPDATE ... status = 'CONNECTED'` never checked its affected row count, so a connection deleted mid-flow (disconnect racing an in-progress authorization) would have silently reported success without actually connecting anything; it now checks `rowCount` and reports `409` honestly. A third, smaller gap closed by review rather than a failing test: `setFolder`'s `invalid_grant` handler updated `status = 'NEEDS_REAUTH'` with no status guard in its `WHERE` clause, unlike the equivalent path in `syncConnection` — now consistent.

**Deliberately not built.** Per-org AI provider choice — a Drive-imported file still uses the one server-wide `CAPTURE_AI_PROVIDER`. A second Drive folder or a second connected Google account per organization (`ux_ap_flow_drive_connections_org` is `UNIQUE (org_id)` by design). OAuth application verification with Google — an unverified app shows Google's own warning screen and is capped at a small number of test users, accepted for a portfolio build. Drive push notifications — polling only; this dev setup has no public HTTPS endpoint to receive one. An outbox event or webhook firing on an import.

## Phase 19.3, as delivered

**Built 2026-09-17, the same day as 19.2 — a rework prompted by a direct question: could Drive intake be simpler to connect, and could one folder feed more than one app?** Two independent decisions came out of that: authenticate with a Google service account instead of requiring every tenant to walk an OAuth consent screen, and let a folder declare what it's *for* so its files route to the app that actually parses that kind of document.

**Why a service account, concretely.** OAuth's `drive.readonly` scope is Google-classified **restricted** — real production use needs an annual third-party security assessment, not just a review. Worse for a project like this: an OAuth app in Google's **"Testing" publishing status is issued refresh tokens that expire after 7 days**, so a 19.2-style connection would have silently died weekly. A service account authenticates as itself via RFC 7523's JWT-bearer grant — no consent screen, no Google verification, and structurally no refresh token to expire, because there is nothing to refresh: a fresh signed assertion trades for a fresh access token any time, using only a key already held locally. The tenant grants access by sharing a folder with the service account's address, exactly as they'd share with a colleague. OAuth is **retained**, not removed, as the fallback for a Workspace tenant whose admin blocks external sharing.

**Why folder purpose, concretely.** 19.2 hard-coded one folder per org, feeding AP-Flow only. Two real parse destinations already existed in the codebase before this phase — AP-Flow's vision pipeline (PDF/PNG/JPEG → OCR → bill) and LedgerCore's CSV bank-statement parser — with no intake path connecting Drive to the second one. A folder now declares `VENDOR_BILL` or `BANK_STATEMENT`, and many folders can exist per org.

**The promotion, and its rule-16 justification.** With two destination apps, the integration could no longer honestly live under `/api/v1/capture/drive` — it moved to `/api/v1/integrations/drive`, alongside `/documents` and `/ai-usage` as platform-level infrastructure belonging to no single app slug. The actual routing is `services/integrations/driveIntakeDispatcher.ts`: a `switch` on purpose calling exactly one function per branch — `captureDocumentService.captureFile` or `bankImportService.importStatement`, each app's own public service, never its tables. The file contains zero SQL, provably (`grep -c "pool\.query\|client\.query"` returns `0`), and a third purpose is a compile error until the dispatcher's exhaustiveness check is updated. See [study/architecture/modular-monolith-app-namespacing.md](../study/architecture/modular-monolith-app-namespacing.md).

**The table rename, signed off.** `ap_flow_drive_connections` → `integration_drive_connections`, `ap_flow_drive_files` → `integration_drive_files`, both in a new migration (053) that never touches 052's own file — rule 13's protection is for the file that created a table, not the table's name forever. Every constraint and index kept its 052-era name through the rename (Postgres renames only the table itself) until 053 explicitly renamed those too, driven from a `pg_constraint`/`pg_index` catalog loop rather than a hand-typed list, since several names are Postgres-auto-generated and a wrong guess would fail the whole migration. See [study/postgresql/migrations-and-schema-evolution.md](../study/postgresql/migrations-and-schema-evolution.md).

**Four real defects fixed, found while re-deriving this design rather than by a failing test:**
1. **The due-query never used `last_synced_at`.** 19.2's `listConnectionsDueForSync` had no time predicate at all despite the column existing — every connected org was swept every tick, relying entirely on the sweep handler's time-bucketed jobId to avoid re-enqueueing. The new `listFoldersDueForSync` filters on it directly.
2. **No incremental cursor.** Every 19.2 sync re-listed the entire folder from scratch. Each folder now carries `drive_cursor`, a `modifiedTime` high-water mark passed as `listFolderFiles`'s `modifiedSince` option, rewound by 60 seconds from the newest timestamp seen (Drive's `files.list` is not a snapshot, so a file can surface with a timestamp slightly behind one already returned) — and advanced **only** when a listing came back both complete (under the per-sync cap) and error-free, so a truncated page or one file's transient failure can never be silently skipped on the next poll.
3. **No protection against an overlapping sync.** At 19.2's 5-minute poll this never mattered; at 19.3's ~60-second poll a slow sync can plausibly still be running when the next tick fires. `syncFolder` now claims its folder with a single conditional `UPDATE ... WHERE (last_synced_at IS NULL OR last_synced_at < now() - interval) RETURNING ...` before doing any work — `rowCount = 0` means someone else already has it, no lock needed, the row's own predicate is the lock.
4. **`resetTables()`'s test helper never listed the Drive tables.** Confirmed absent from the TRUNCATE list at `factories.ts` — 19.2's Drive rows leaked between test files. Fixed in the same pass.

**The legacy callback, kept deliberately.** `GOOGLE_OAUTH_REDIRECT_URI`'s default moved with the route, from `/api/v1/capture/drive/oauth/callback` to `/api/v1/integrations/drive/oauth/callback`. Anyone with the old value pinned in `.env` would otherwise 404 with nothing explaining why, and fixing it means hand-editing the Cloud Console's authorized-redirect list — so `routes/capture/driveRoutes.ts` shrank to exactly one route, the callback alone, kept until no `.env` in use still names the old path.

**A Redis-resident scheduler does not follow a code rename.** `upsertJobScheduler`'s repeatable-job state lives in Redis, keyed by an id the code chose — renaming the queue in TypeScript does nothing to the old scheduler already ticking there. `startWorkers` explicitly calls `removeJobScheduler('ap-flow-drive-sweep-tick')` once, or it would have fired forever against a queue no worker consumes. See [study/architecture/background-jobs-and-queues.md](../study/architecture/background-jobs-and-queues.md).

**Client.** The Drive card moved off `ApFlowSettingsPage.tsx` (which now only links to it) onto a new platform page, `/integrations`, alongside `/documents`. The service-account path is the default: the page shows the address to share with, a copy button, and — only when OAuth is also configured — a secondary "Connect with your Google account instead" link. Each folder is its own card: purpose, an account picker and date-format select for `BANK_STATEMENT`, sync-now, and a `ConfirmDialog`-gated remove.

**Acceptance ✅ — verified.** `npm run migrate` applies migration 053 idempotently, twice. Full server and client suites pass, zero regressions. Cross-tenant isolation proven at both the service layer (`syncFolder` against another org's folder id writes to neither organization; a `BANK_STATEMENT` folder naming another org's account fails `422 Bank account not found`, never a leak) and the HTTP layer (`GET`/`PATCH`/`DELETE` on another org's folder all 404, never 403; a forged `orgId` in the query, a header, and the body together produce a byte-identical response to the honest request).

**Deliberately not built.** Google Sheets in a watched folder — `alt=media` cannot export a Google-native file; a Sheet is simply never listed. Drive push notifications — still polling only; `files.watch`/`changes.watch` need a publicly reachable HTTPS endpoint with a CA-signed cert and, for `changes.watch`, are whole-drive rather than folder-scoped regardless. A `RECEIPT` or AR-invoice folder purpose — no parser exists for either yet. Re-import when a Drive file is edited in place (the dedupe key is the Drive file id, not its content or `modifiedTime`). An outbox event or webhook firing on an import. Folder-level RBAC finer than the connection's own OWNER/ADMIN gate. Service-account key rotation tooling — rotating means generating a new key in the Cloud console and redeploying by hand.

## Phase 19.4, as delivered

**Built 2026-09-18, a real bug reported from actually using Phase 19.3.** Uploading a renamed copy of an already-captured invoice through a Google Drive folder was imported (the Drive-intake log recorded `IMPORTED`) but never appeared anywhere in AP-Flow's document list — no new row, no error, nothing to act on. The Document Vault is content-addressed by SHA-256, so identical bytes under a different filename resolve to the same vault row; AP-Flow's own `ap_flow_documents.document_id` carried a `UNIQUE (org_id, document_id)` constraint that made a second registration of that vault row physically impossible, so `captureFile` silently returned the pre-existing registration instead. The fix: a second capture is now a real, visible event.

**The fix, mechanically.** `ux_ap_flow_documents_document` is dropped (migration 054) — a second AP-Flow registration of the same vault document is now legal by design. A new `duplicate_of_id` self-referencing column (composite FK, `ON DELETE SET NULL`) and a new `DUPLICATE` status let `captureDocumentService.createApFlowDocument` — the single function every entry point funnels through (direct upload, the two-step vault-picker registration, and Drive folder sync all call it, none re-implement the check) — decide, inside the same transaction as the `INSERT`, whether a new row is a genuinely new capture or a repeat of one already on file. A `DUPLICATE` row enqueues no extraction (no AI spend on a capture nobody has confirmed is worth processing) and carries `duplicateOfId` pointing at the earlier row. `DUPLICATE -> PENDING` is a legal FSM edge, identical in shape to `FAILED -> PENDING`, so "this is not actually a duplicate — process it" reuses the existing `POST /documents/:id/reextract` action verbatim; no new endpoint exists. `duplicateOfId` is deliberately left in place afterward as history rather than cleared.

**Two migrations corrected two real mistakes in the first one, both caught by the tests written for this same change, not by later inspection.** 054's original CHECK — `(status = 'DUPLICATE') = (duplicate_of_id IS NOT NULL)`, a biconditional — made it impossible to push a duplicate through to `PENDING` while keeping `duplicateOfId` as history, since the CHECK forced clearing it in the same statement; 055 relaxed it to one-directional (`status <> 'DUPLICATE' OR duplicate_of_id IS NOT NULL`). That in turn collided with the FK's own `ON DELETE SET NULL`: deleting the row a `DUPLICATE` points at nulls `duplicate_of_id` while leaving `status` untouched, and Postgres re-validates every CHECK against the row a cascade produces — so a still-`DUPLICATE` row with a freshly-nulled pointer violated the very constraint meant to guard that pairing. 056 drops the CHECK entirely: there is in fact no `DELETE` route anywhere on `ap_flow_documents` today, so the FK action is defensive plumbing for a case the application never triggers, and the real invariant ("a `DUPLICATE` row is never created without a target") is fully guaranteed by the one function that ever sets this status. See [study/postgresql/migrations-and-schema-evolution.md](../study/postgresql/migrations-and-schema-evolution.md).

**Client.** `ApFlowDocumentsPage`'s status filter and pill gain `DUPLICATE` (amber, "Possible duplicate") — the pill's previous unconditional fallback to red "Failed" for anything unmatched would have mislabelled it had this not been added explicitly. The document detail page shows an amber banner naming the earlier capture with a link to it, and relabels the reextract button and its confirmation dialog to "Not a duplicate — process it" / "Process it" when the document is `DUPLICATE`.

**Acceptance ✅ — verified.** `npm run migrate` applies 054–056 idempotently, twice. Full server and client suites pass, zero regressions. A dedicated regression test reproduces the exact reported bug at the dispatcher level: the same PDF bytes arriving as two different Drive files (one renamed) both report `IMPORTED`, the second as a genuinely new row with `status = DUPLICATE` and `duplicateOfId` pointing at the first. Direct upload, the two-step registration route, and Drive intake are each covered by their own case proving the identical behavior — the whole point of centralizing the check in one function.

**Deliberately not built.** Cross-organization duplicate detection — two different orgs uploading the same invoice never see each other's rows (rule 1), which also means the vault's own content-addressing is per-org, not global; this fix operates entirely within that existing boundary. A "merge" action that consolidates a confirmed-duplicate's line items or history into the primary document. Any UI affordance for browsing *all* of an org's duplicate flags at once (today: the general document list, filtered by status, same as any other status).

## Phase 6.1, as delivered

A half-step off Phase 6, in the 3.5–3.9 lineage — discovered mid-build, not planned in advance, so it appears only as this delivered section and carries no row in the phase table above. **Renumbers nothing**, and does not collide with the already-reserved Phase 20 ("a verification sweep," unstarted — see the table note above).

**Built 2026-09-20, LedgerCore.** Closed the one functional gap docs/accounting.md's "Not built yet" section named explicitly since Phase 6: a bank line with no counterpart document — a bank fee, interest earned, an opening capital deposit — could only be filed under `IGNORE`, which drops it from the reconciliation report's statement side entirely rather than settling it against the GL. A line that genuinely moved cash had no honest resolution.

**The fix.** `POST /bank-transactions/:id/post-journal` posts a balanced two-line journal entry directly from the bank line — a deposit debits the bank account and credits the chosen account, a withdrawal is the reverse — through `journalService.createEntryOnClient` with `sourceType: 'bank_line'`, `sourceId` = the bank transaction id, exactly the same boundary `matchTransaction` already respects for `paymentService` (rule 16: no direct `ledger_lines` write from `bankMatchService`). A `MATCHED` line now settles exactly one of two ways — a matched payment, or a direct journal posting — never both, never neither. `reject_bank_transaction_mutation()`'s carve-out list grows to exempt the new column, or the immutability trigger the same migration relies on would reject the very `UPDATE` this feature performs. `unmatch` gained a parallel branch: it reverses the journal entry (never deletes it, rule 6) exactly as it already voided a matched payment, and clears both possible match-state columns unconditionally.

## Phase 25, as delivered

A direct feature request in the same convention as Phase 24: 20–23 stay reserved, and this takes the next free number. LedgerCore gains **customer and vendor accounts**, a clickable subsidiary ledger per party, and the posting rule that keeps those ledgers provably equal to the GL.

**The accounting decision.** Each customer or vendor does **not** become a GL account. The chart keeps one receivable control account (`1120` or `ledger_invoice_settings.receivable_account_id`) and one payable control account (`2100` or `ledger_settings.payable_account_id`). Each party's account is a subsidiary ledger underneath, and the trial balance, P&L and balance sheet are unchanged: they show only the control accounts. This is the standard control-account/subledger model, and how QuickBooks, Xero and SAP all work. A GL account per party was rejected: thousands of chart rows, every new customer a chart change, unreadable statements.

**Party accounts, no migration.** `partyLedgerService.ts` attributes each control-account `ledger_lines` row to a party through the document that posted it: the `journal_entry_id`/`void_journal_entry_id` of that party's invoices, bills and payments, all existing FK-constrained columns. It groups per (journal entry, document), so a payment settling three invoices is one row with the split recovered from `payment_allocations`, then runs the same explicit-`ROWS` window-function running balance as the account ledger. `GET /customers/:id/ledger`, `/customers/:id/open-items`, `/vendors/:id/ledger` and `/vendors/:id/open-items` are all readable by any member. Full detail: [api.md](api.md). The GL-side ledger and the document-side open items are derived independently. **For every party, ledger closing balance = open-items outstanding, and the sum over parties = the aging report's total = the control account's GL balance.** `partyLedger.test.ts` asserts all three for AR and AP. It holds exactly because an invoice or bill with payments applied cannot be voided.

**Journals may no longer post to a control account.** A journal line names no customer or vendor, so a manual journal on AR/AP could only break that tie; `/reports/ar-aging`'s `reconciles` would go `false` permanently. QuickBooks answers this by requiring a Name on AR/AP journal lines; SAP by refusing direct postings to reconciliation accounts (message F5354). This phase takes the SAP route. `journalService.assertNotControlAccountsOnClient` makes `POST /journals` and `POST /bank-transactions/:id/post-journal` return `422` for the control accounts. `createEntryOnClient`, the path invoices, bills, payments and FX revaluation post through, is deliberately unguarded. ## Phase 26, as delivered

A direct feature request in the Phase 24/25 convention (20–23 stay reserved; 24 and 25 are taken). LedgerCore gains the two correcting documents a real AR/AP cycle needs. Plan: `plans/phase-26-credit-and-debit-notes.md` (deleted on delivery).

**Terminology ruling.** The textbook/commercial sense: a **credit note** is issued by us to a customer and reduces AR on an `ISSUED` invoice; a **debit note** is issued by us to a vendor and reduces AP on a `POSTED` bill (QuickBooks' "vendor credit", Xero's "purchase credit note"). The GST-sense seller's debit note that *increases* an invoice is not built — a supplementary invoice does the same job.

**Schema — one migration, `063`.** `credit_notes`/`credit_note_lines`/`credit_note_allocations` and the `debit_notes` mirror (plus `vendor_credit_reference`), per-org `CN-`/`DN-` counters on `ledger_invoice_settings`, `to_jsonb` row-diff immutability (DRAFT editable, then only `ISSUED -> VOID`), insert-only allocations, two deferred constraint triggers (note ≤ its own total and payments + notes ≤ document total; Σ issued notes ≤ original total), and a `CREATE OR REPLACE` of `014`'s `assert_no_overallocation()` so a payment must fit inside what notes left. Full detail: [schema.md § Phase 26](schema.md#phase-26--credit--debit-notes-ledgercore--applied).

**Posting.** Issuing a credit note posts DR each revenue account (usually `4800 Sales Returns & Allowances`) + DR sales tax / CR receivable; a debit note posts DR payable / CR each expense account + CR input tax. Both post at the **original's frozen `fx_rate`**, so applying a note back to its own original is FX-neutral. In the same transaction the note auto-applies to its original up to the amount still due. **Applying** a note (auto or via `POST /:id/allocations`) posts no journal entry — it matches two open items already inside the control account. A foreign-currency note is capped at its original's amount still due, so it never leaves a remainder that would need cross-rate application. Void posts a reversal; allocations stay and stop counting. An original with an issued note against it or applied to it cannot be voided.

**Settlement, redefined in one place.** `services/accounting/settlementSql.ts` now defines "settled" as POSTED payment allocations **plus** ISSUED note allocations, and every amount-due site switched to it: invoice/bill reads and settlement filters, payment validation, bank-match candidates and suggestion re-scoring, FX revaluation exposure, AR/AP aging, party open items. That refactor landed first, before any note existed, and had to keep the full suite green with an unchanged count (1702 passed, 2 skipped). `Invoice.creditedCents` and `Bill.debitedCents` are new derived fields.

**Subledger.** An issued note's **unapplied** remainder is a negative open item (always `CURRENT`) in AR/AP aging and party open items; every `outstanding > 0` filter became `<> 0`. Party ledgers gain `CREDIT_NOTE`/`CREDIT_NOTE_VOID`/`DEBIT_NOTE`/`DEBIT_NOTE_VOID` rows. Phase 25's invariant, per party ledger closing = open-items outstanding and Σ parties = aging total = control balance, still holds with a credit balance on the books (`noteSettlement.test.ts`).

**Client.** One parameterised set of note components (`client/src/Pages/notes/` — list, form, detail with Issue/Void/Delete confirmations and an Apply-credit dialog) behind thin credit/debit page wrappers; sidebar entries under Sales and Purchases; **Create credit note** on an issued invoice and **Create debit note** on an approved expense (the form pre-fills the original's lines, defaulting a credit note's account to `4800`); credits/debits-applied rows and a notes list on the invoice/expense pages; note rows and negative open items on the party account page.

**Walkthrough — month 4, "Returns & adjustments".** `walkthrough/08-returns-and-adjustments.md` explains what each note is, when you need one (and when you don't), the journal entry each posts, and why applying posts none; then the user enters CN1 (a sales return on unpaid I15), DN1 (a supplier return on unpaid B12, with the vendor's credit-note number) and CN2 (a price allowance on I13, paid in month 3, which sits as −500.00 unapplied credit on Ferrous Works' account until applied to I16), and imports a fourth statement whose three settlement lines are for the *net* amounts. `walkthrough.test.ts` replays all four months through the real API and asserts the reports equal the computed answer key cent for cent, including the −500.00 checkpoint and `reconciles: true` while it's outstanding. Months 1–3's statement CSVs are byte-identical to before.

**Deliberately not built.** Cash refunds of unapplied credit (a refund must be bank-matchable to keep the reconciliation tying); a bad-debt write-off document; the GST-sense supplier debit note; applying a foreign-currency note to a document other than its original; outbox events/webhooks for notes; PDF/email of notes; a settings UI for the `CN-`/`DN-` prefixes; notes in the sandbox dataset; BoardDeck close checks aware of draft notes; notes from AP-Flow capture; re-scoring existing bank suggestions when a note is issued after a statement was imported. **Pre-existing gap surfaced, not fixed:** the aging report's open-document set is current state — it does not filter documents by their own date — so an `asOf` earlier than an already-entered document shows that document but not its GL line; the walkthrough's mid-month checkpoint is dated accordingly.

**Acceptance ✅ — verified.** `creditNotes.test.ts` / `debitNotes.test.ts` (17 cases each: posting shape, auto-apply, fully-paid → unapplied, cross-apply and its refusals, cumulative and foreign-currency caps, draft edit/delete vs issued, void re-opening the original, original-void refusal, a locked-period rollback that burns no number and writes no journal, VIEWER 403, and cross-tenant 404/422 on read, create, apply, list and void); `creditNoteConstraints.test.ts` / `debitNoteConstraints.test.ts` (9 each, straight at the pool: immutability, insert-only allocations, every deferred cap with its exact message, `chk_*_total`); `noteSettlement.test.ts` (7: negative open items, party ledger rows, reconciles before/after apply and after void, AP mirror, the bank matcher scoring the credited amount due at 100, cross-tenant); the four-month walkthrough replay. **1763 server tests (2 skipped, the gated live-provider cases) + 296 client tests** — full clean runs, zero regressions. Study notes: new [credit-and-debit-notes.md](../study/architecture/credit-and-debit-notes.md); extended [deferred-constraint-triggers.md](../study/postgresql/deferred-constraint-triggers.md), [subledger-reconciliation-and-aging.md](../study/postgresql/subledger-reconciliation-and-aging.md), [gapless-numbering-and-counters.md](../study/postgresql/gapless-numbering-and-counters.md).

## Phase 32, as delivered

A direct feature request ("the inventory *is* StockLedger; the items and services we add there should be used by LedgerCore; StockLedger houses assets, inventory, even office supplies — build it to industry standard"), outside the strategic-plan sequence that still reserves Phases 20–23 — numbered like Phases 24 and 30. **Step 1 of two is delivered**; step 2 is listed under "Deliberately not built". Migrations `071` and `072`.

**One product master — the Zoho Books + Zoho Inventory model.** LedgerCore's `items` table (Phase 24) is the single master, renamed **Products & Services** in the UI, and gains `item_type`: `SERVICE`, `NON_INVENTORY` (goods bought or sold but not quantity-tracked — office supplies expensed on purchase), `INVENTORY` and `FIXED_ASSET` (reserved; nothing can create one yet, so step 2 needs no migration). **Where do standard services get created? In LedgerCore → Products & Services** — services and non-inventory items are created there; inventory items are created in StockLedger, which creates the linked product in the same transaction. `kind` (migration `059`, never edited — rule 13) stays, tied to `item_type` by a CHECK and always derived from it in the service. The API still accepts the Phase 24 `kind` (`GOODS` maps to `NON_INVENTORY`). `INVENTORY`/`FIXED_ASSET` items carry `asset_account_id` and `cogs_account_id` (a CHECK forbids them on any other type); their name and active flag are owned by StockLedger and pushed to the product by `syncLinkedItemOnClient`, so `PATCH /items/:id` refuses them.

**The link lives on the dependent side.** `stock_items.ledger_item_id` — unique per org, frozen by a trigger once set, **no `REFERENCES`** (rule 16 overrides rule 8, the ruling `032` made for AP-Flow's account ids in the other direction; the service validates and items are never deleted). StockLedger `requires: ['ledger-core']` now. A stock item created before this phase is linked on request (`POST /stock/items/:id/link-product`), which posts an opening entry (Dr Inventory / Cr 3400) for the stock it already holds — not done in a migration because a code can collide with an existing product and the opening entry needs a user, an open period and the audit context.

**Documents move stock through one seam.** `services/inventory/documentStockService.ts` is the only StockLedger module LedgerCore imports. A bill line for an `INVENTORY` product **receives** stock at its net value in **base currency** (an inventory account's net total is converted once, then split across its lines with `allocateCents` so the receipts add up to the GL debit to the cent; recoverable tax stays on the input-credit account); an invoice line **issues** stock at the current moving average and the same journal entry gains Dr COGS / Cr Inventory. LedgerCore builds its own journal from the values the seam returns — StockLedger writes no journal line for a document. Everything runs on the caller's transaction client (rule 5). **Lock order: document row → all of the document's stock balances in one sorted pass → invoice-number counter → journal.** `issueInvoice` therefore allocates the number *after* the stock issue, so a 409 for short stock leaves a DRAFT with no number consumed. `movementService` was split into `*OnClient` cores with thin `withTransaction` wrappers; the four routes behave as before.

**Provenance and voids.** `stock_movements` gains `source_type`/`source_id` (mirroring `journal_entries`), `gl_account_id` (the inventory account the value posted to; NULL = never touched the GL) and `reverses_movement_id`, plus movement types `RECEIPT_REVERSAL` and `ISSUE_REVERSAL`. Movements stay append-only — a void is a new row, and a partial unique index stops one being reversed twice. **Invoice void:** stock returns at the *exact* issued value (the reversing entry already mirrors the COGS lines). **Bill void:** refused with 409 if less than the received quantity is still on hand; otherwise the original value is removed, clamped to what the balance still holds, and any clamped difference is re-posted as a variance entry (Dr Inventory / Cr 5400) so stock and GL stay equal. Removing at the *current* moving average was rejected: 10 @ $5 then a receipt of 10 @ $10, voided, must leave $50, and the average leaves $75.

**Manual StockLedger movements of a linked item post a journal in the same transaction** (`stockGlService`): receipt → Dr Inventory / Cr Opening-stock equity (3400) — for a linked item a purchase should be a bill, so a manual receipt is treated as opening stock; issue and adjustment-out → Dr 5400 / Cr Inventory; adjustment-in → the reverse; transfers post nothing. **Behaviour change:** a linked item's movement dated in a closed fiscal period now fails with 422 and the stock does not move. Unlinked items behave exactly as in Phase 28.

**Accounts.** Two new postable default accounts — `5050 Cost of Sales — Inventory` and `5400 Inventory Adjustments & Shrinkage` (5000 is a non-postable header) — seeded for new orgs (`DEFAULT_CHART`, 47 accounts, 37 postable) and existing ones (migration `071`, the `028` pattern). `ledger_settings` gains `inventory_account_id`, `cogs_account_id`, `inventory_adjustment_account_id`, `stock_opening_account_id`. Posting uses the item's own account, then the settings account, then the default chart code — each checked for type and postability, so an imported chart that already uses 5050 for something else fails with a readable 422 instead of posting to the wrong account. `stock_settings.default_location_id` (set automatically to the profile's main location when a profile is applied, editable on the Locations page) is where a line lands when it names none; `invoice_lines`/`bill_lines` gain `stock_location_id` (no FK — rule 16).

**A sixth integrity check**, `stock_movements_reconcile_with_gl` (`npm run verify:integrity`): for every (source, inventory account) a set of GL-linked movements posted to, the movements' value equals the net debit on that account across the source's journal entries, reversals included (a reversal copies `source_type` but not `source_id`, so it is joined back through `reverses_entry_id`). Scope stated openly: it reconciles each *document* with its movements, not the whole inventory account with total stock value.

**Client.** `ItemsPage` becomes Products & Services with type tabs, on-hand quantity and "Open in StockLedger" for stock-managed rows, and a create form limited to `SERVICE`/`NON_INVENTORY`; the invoice and bill pickers group every product by type, show on-hand, disable lot/serial items and fixed assets with a reason, add a per-line location select for inventory items, and on a bill lock an inventory line's account; `StockNewItemPage` gains an accounting section (prices, revenue/inventory/COGS accounts); the item detail page shows the linked product (or a "Link" action) and a Source column on movement history; the Locations page holds the default-location select. **Quick add:** the item picker ends with "＋ New product or service…", which opens `QuickAddProductDialog` (a portal, so it is not a `<form>` nested in the document form, with `stopPropagation` so "Create and use" never submits the draft) to create a `SERVICE` or `NON_INVENTORY` product — name, type, price, account — through the same `POST /items` (no new endpoint), then picks it on that line. The code is derived from the name and retried with `-2`, `-3` … if taken; a code the person typed is never silently changed. Inventory items are deliberately not offered (stock needs a unit, tracking and a location, owned by StockLedger); free-text lines remain available and unchanged.

**Tests.** `inventoryPosting.test.ts` (25 — bill receipt, FX, multi-line rounding, invoice COGS, 409, voids incl. variance, manual movements, closed period, link, cross-tenant), `documentConcurrency.test.ts` (last-unit race; opposite line orders, repeated), `documentConstraints.test.ts` (migration `072` CHECKs, frozen link, single reversal, append-only, integrity tamper), `itemTypes.test.ts`; account counts in `accounts.test.ts`/`reports.test.ts` moved 45→47 / 35→37 (a new default chart, not a weakened test); the app-selection tests that used StockLedger as "an app with no requirements" now use LedgerCore. ## Phase 34, as delivered

A direct feature request, numbered like 24/30/32/33 outside the strategic-plan sequence that still reserves 20–23. Two features that remove repetitive bookkeeping work, both accounting-module only (`MODULE_TAGS.accounting`), no new dependency.

**Step 0 — database restore.** Before any new migration could be written, the dev database `autodb` and the test template `autodb_test` had to be brought back in line with the checked-in schema: both still carried the **withdrawn** `074_platform_drop_vestigial_columns.sql` from Phase 33 (six columns dropped, never released as a real migration). The six columns were restored NULL-filled and the stray `schema_migrations` row deleted, freeing the `074` prefix. See [Phase 33 § Known issues, now resolved](#phase-33-as-delivered).

**34a — bank rules.** A saved pattern — "memo contains STRIPE FEE, post to 6600 Bank Fees" — settles a matching bank line the same way a human already could through `POST /bank-transactions/:id/post-journal`, either automatically on every `POST /bank-imports` or on demand via `POST /bank-rules/apply`. Migration `074_ledger-core_bank_rules.sql`: table `bank_rules` (`priority`, `direction`, `memo_contains`, an inclusive `amount_min_cents`/`amount_max_cents` range on the line's absolute amount, an optional `bank_account_id` scope, `target_account_id`, `is_active`), plus `bank_transactions.matched_rule_id` with `chk_bank_txn_rule_needs_journal` (a rule match always implies a posted journal entry) and a fourth column added to `reject_bank_transaction_mutation()`'s "only the match state may change" carve-out. `bankMatchService.postJournalForTransaction` was split into a transaction-owning wrapper and a `postJournalForTransactionOnClient` core so both a human action and a rule share one posting path. Matching is deterministic — `utils/bankRuleMatch.ts`'s `findMatchingRule`, no scoring, no learning — and **a document suggestion at or above `AUTO_MATCH_THRESHOLD` (85) always wins over a rule**, so a rule only ever claims a line a real invoice/bill match did not already want. Each candidate line applies inside its own `SAVEPOINT` in the import's transaction, so one rule's posting failure (a closed period, the Phase 25 control-account guard) rolls back just that line and leaves the rest of the import to commit — see the new study-note SAVEPOINT section. `POST /bank-rules`, `GET /bank-rules`, `PATCH /bank-rules/:id`, `POST /bank-rules/apply`; a client page at `/bank/rules`, and a "Create a rule from this line" link from a just-settled bank transaction.

**34b — recurring documents.** An invoice, bill or manual journal entry becomes a template a background sweep turns into the next occurrence on schedule, as a draft or posted document, **exactly once** per due date; a recurring journal can additionally auto-reverse on the first day of the next month (e.g. a monthly accrual). Migration `075_ledger-core_recurring_schedules.sql`: `recurring_schedules` (`kind`, three mutually-exclusive nullable `source_*_id` FKs rather than one polymorphic id — rule 8 — enforced unrepresentable-in-the-database by `chk_recurring_source_matches_kind`, `frequency`/`interval_count`, `start_date`/`end_date`, `next_run_date`/`next_occurrence_index`, `mode`, `auto_reverse`, `status`, `last_error`) and append-only `recurring_runs` (one row per generated occurrence, `UNIQUE (schedule_id, run_date)`). Occurrence dates are always computed from the schedule's **anchor** `start_date`, never from the previous occurrence, so a 31st-of-the-month schedule never drifts to the 28th (`utils/recurrence.ts`). Exactly-once generation is two layers deep: `recurring_schedules ... FOR UPDATE SKIP LOCKED` before generating, plus the `UNIQUE (schedule_id, run_date)` constraint as a second line of defence if the lock discipline were ever bypassed by a bug. `invoiceService`/`billService` gained `createInvoiceOnClient`/`issueInvoiceOnClient`/`createBillOnClient` cores (the same wrapper/core split as 34a) so the sweep can create and, in `POST` mode, issue/approve a generated document inside one transaction with its `recurring_runs` row. The sweep is a BullMQ scheduler (`recurring-sweep`, every 15 minutes — `RECURRING_SWEEP_INTERVAL_MS`) that enqueues one `recurring-generate` job per due schedule, the same sweep-then-per-entity-job shape Phase 19.3's Drive intake introduced; `listDueSchedules` is a documented, ids-only, cross-org exception to rule 1, exactly like `driveSyncService.listFoldersDueForSync`. A schedule that falls behind (the worker was down) catches up at most `RECURRING_MAX_CATCHUP_PER_RUN` (12) occurrences per sweep tick, not unboundedly. `GET`/`POST /recurring-schedules`, `POST /:id/pause`, `/resume`, `/end`, `/run`; client pages at `/recurring` and `/recurring/:id`, and a `MakeRecurringDialog` opened from an invoice, bill or journal entry's detail page.

**Known deviations from the approved plan, recorded honestly:**
- The approved plan put a separate "Recurring" nav entry under Sales, Purchases and Accounting. This build uses **one** `/recurring` page with a kind filter, under Accounting, because three entries would open the same page.
- `schemas/accounting/recurringScheduleSchema.ts` validates `startDate`/`endDate` with `z.string().date()` rather than `z.iso.date()` — equivalent runtime behaviour (both require a `YYYY-MM-DD` string), just a different zod spelling than the plan named.
- The recurring sweep runs every 15 minutes, not on any other cadence the approved plan may have implied.

**Tests.** 1673 server tests passing (2 skipped — the pre-existing gated live-provider cases, unchanged) across 133 files, up from 1610. 439 client tests passing across 66 files, up from 428. `npm run verify:integrity` passes all six checks. Migrations `074` and `075` apply idempotently, verified by the replay test on the restored databases. `recurringSchedules.test.ts` carries 18 cases, including `'an invalid kind filter is a 400'` — a real bug this docs-sync pass found (`GET /recurring-schedules` threw an uncaught `ZodError` on a bad `?kind=`/`?status=` instead of answering `400`) and which was fixed in the same phase, not carried forward as debt.

**Guardrail review:** zero violations.

**Manual smoke test, through the real API:** a bank rule settled the walkthrough month-1 fee line on import; running a recurring invoice's `POST /:id/run` twice on the same day produced exactly one new draft invoice, not two.

**Deliberately not built.**
- Rules that match a party, or split a settlement across several accounts.
- Rules learned automatically from posting history.
- Recurring credit notes or debit notes.
- Editing a schedule in place — end it and create a new one.
- Emailing a generated invoice.
- Catch-up beyond 12 occurrences in one sweep tick.

## Cross-cutting infrastructure

**Audit trail & CDC (Phase 5) ✅ delivered — see [Phase 5, as delivered](#phase-5-as-delivered).** System-wide PostgreSQL triggers capturing `OLD` and `NEW` row states into a centralized, immutable `audit_logs` table as `JSONB`, alongside `org_id`, actor `user_id`, client IP, table name, operation, and timestamp — shared across every app. A trigger cannot see `req`, so the actor and IP reach it through `set_config('app.current_user_id'/'app.client_ip', ..., true)` set inside the same transaction and read back with `current_setting(..., true)`. This is distinct from `updated_at` timestamp triggers — write both, but do not confuse one for the other.

Phase 5 also shipped **`npm run verify:integrity`**: a standalone checker asserting that total debits equal total credits across the entire database, that every journal entry balances individually, and that no ledger line is orphaned. It is the script you run in front of an auditor, and it is proven able to fail (`server/src/__tests__/integrity.test.ts`).

**Background jobs (Phase 7) ✅ delivered — see [Phase 7, as delivered](#phase-7-as-delivered).** `bullmq` + `ioredis`, a worker process, retry/DLQ policy — shared infrastructure AP-Flow builds on today. ForecasterPro, BoardDeck Automator and TaxGuard AI also built on it before their Phase 29 retirement.

Phase 7 also delivered **financial-event webhooks** — an outbound notification when a watched condition fires, e.g. a large unmatched bank transaction reaching the ledger. Webhooks landed here and not earlier because rule 5 forbids post-`COMMIT` follow-up work: an HTTP call to a receiver cannot be made inside the posting transaction, and firing it after `COMMIT` without a queue means a crash between the two silently loses the notification — the transactional outbox this phase built is exactly the mechanism that closes that gap.

**Onboarding state (Phase 9).** `onboarding_states`, one row per `(org_id, app_slug)`, is platform infrastructure rather than LedgerCore's: every app that acquires a setup wizard gets skip-and-resume for free, and the suite-level checklist reads across all of them. See [Phase 9, as delivered](#phase-9-as-delivered).

**Document storage (Phase 9.5) — promoted from AP-Flow.** The suite retains uploaded documents on the local filesystem under `server/storage/`, org-scoped and named by SHA-256, with metadata in a platform `documents` table and per-app attachment rows in `document_links`. This is deliberately the simplest thing that satisfies the audit requirement, and it does **not** survive a multi-instance deployment; the storage service keeps a narrow interface (`put(orgId, buffer) → hash`, `get(orgId, hash) → stream`) so object storage is a one-file swap when deployment becomes real. It was AP-Flow-owned until 2026-09-10 — see the [renumbering entry](#phase-renumbering--2026-09-10) for why it moved and why the path is keyed by organization rather than globally content-addressed.

**Dev tooling — `./dev.sh` (not a phase).** Collapses the three-terminal startup (Postgres/Redis, server, worker, client) into one command, adding no dependency. It is the process-group counterpart of the per-process drains already in `index.ts`/`worker.ts`: `set -m` puts each spawned child in its own process group so one `kill -TERM "-$pgid"` reaches the whole `npm → tsx → node` chain, which `npm` alone will not forward a signal into. See [docs/development.md](development.md).

## Dropped from scope

The prior roadmap (Phases 6–14, before this restructure) planned Inventory & WMS, Procurement/P2P, Manufacturing/MRP, HR & Payroll, QMS, CRM, and EAM as modules of one ERP. None of that scope survives the restructure — three apps (LedgerCore, AP-Flow, StockLedger) are the suite now; five more were built and then retired in [Phase 29](#phase-29-as-delivered). The engineering patterns those modules would have demonstrated are kept here only as a record, since some are genuinely interesting interview material even though nothing will be built against them:

- **Inventory & WMS** — **superseded by [Phase 28](#phase-28-as-delivered), StockLedger.** Master-plan decision D1 was approved for inventory only (2026-09); the pattern originally sketched here — pessimistic locking (`SELECT ... FOR UPDATE`) on stock rows, an append-only movement ledger, current quantity always derived, never a mutable counter — is exactly what Phase 28 built, plus industry-specific catalogues, custom attributes, configurable item codes and QR labels the original sketch didn't anticipate. ProcureFlow, MakeFlow, PeopleCost and AssetBook (the rest of D1) remain dropped.
- **Procurement / P2P** — FSM-enforced status progression; automated 3-way matching (the pattern AP-Flow now owns instead).
- **Manufacturing / MRP & BOM** — `WITH RECURSIVE` CTEs to resolve nested component trees; mandatory cycle detection.
- **HR & Payroll** — batch processing via cron-triggered jobs; `EXCLUDE USING GIST` constraints (requires `btree_gist`) to make overlapping leave ranges physically impossible.
- **QMS** — customer-definable inspection forms as `JSONB`, validated with `Ajv`, schema-versioned.
- **CRM** — full-text and fuzzy search via `pg_trgm` trigram indexes.
- **EAM** — nightly cron job computing depreciation and auto-posting balancing journal entries; must be idempotent.

**MagicJournal**, the prior build's rule-based keyword-scoring engine that drafted journal entries from plain English, is also dropped rather than revived — TaxGuard AI's RAG approach supersedes the idea it was reaching for, done properly this time (a database-backed, `org_id`-scoped corpus instead of a tracked CSV mutated at runtime).
