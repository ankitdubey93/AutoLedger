# Deterministic Demo Fixtures: Seeding Through the Application, Not Around It

> The obvious way to fill a demo database is a SQL dump or a script of raw `INSERT`s. This codebase's sandbox dataset does neither — it replays 24 months of history through the exact same services the UI calls, which means the data-generation code accidentally became the most thorough exercise of the real business logic this project has ever run in one sitting, and surfaced real bugs a unit test never would have.

**Category:** Architecture
**Introduced by:** Phase 18 — the sandbox dataset, seeded through `invoiceService`, `billService`, `bankMatchService`, and five other apps' own services rather than any raw SQL.
**Verified against:** this codebase's own seeder, PostgreSQL 16, run end to end against a live database.

---

## Mechanism

**Why replay through services rather than `INSERT`:** a double-entry ledger's correctness lives in triggers (the deferred balance-invariant check, posted-row immutability), a document's correctness lives in an FSM (`DRAFT → ISSUED`, `PENDING → PROCESSING → EXTRACTED`), and the audit trail's correctness lives in CDC triggers that fire on `INSERT/UPDATE/DELETE`. A raw `INSERT` into `invoices` bypasses every one of those — the row would look right and prove nothing, and `npm run verify:integrity` (which checks a real invariant, not a fixture) would either pass vacuously or fail in a way that has nothing to do with whether the seeding is "good data." Calling `invoiceService.createInvoice` then `issueInvoice` instead means the same balance trigger, the same FSM guard, and the same audit trigger that a real user's click would fire, fire here too. A seeded invoice is *indistinguishable* from a hand-entered one — not merely similar to it.

**Two rules govern every fixture file, both restating an existing guardrail at a new boundary.** Dates are relative (`monthOffset: -23..0`, resolved against an anchor month at load time via `Date.UTC(year, month - 1 + offset, day)`, which lets JavaScript's own date normalization absorb month/year rollover for free) rather than absolute — an absolute date is correct on the day it's written and wrong every day after, since the display window a cohort matrix or a fiscal-year boundary uses is always relative to *today*. Money is a decimal string (`"1450.00"`), parsed through the same `parseMoneyText` the HTTP boundary already uses, never a bare JSON number — restating guardrail rule 3 ("money is integer cents") at a file boundary instead of a wire boundary, for the identical reason: a JSON number is an IEEE-754 double the instant it's parsed, and there is no point in the pipeline after that where the imprecision can be un-done.

**The orchestrator is a fan-out over one function per app, never a single writer.** `services/sandbox/sandboxService.ts` calls seven `seedSandbox` functions, each living in that app's own service folder and importing only that app's own services (plus, where an app's existing cross-app boundary already sanctions it — BoardDeck reading LedgerCore's `fiscalPeriodService` — that one bridge). The orchestrator itself contains no SQL against any app's table; a `grep` for a forbidden table name across it returns nothing, the identical structural proof every app's own rule-16 boundary already carries. This is not a new pattern invented for seeding — it is the existing cross-app discipline (a named exported function, never a direct query) applied to a new kind of caller.

**Seeding is many transactions, not one.** Each called service opens and commits its own transaction; wrapping the whole load in an outer `BEGIN...COMMIT` here would mean those services running off a client the orchestrator checked out instead of their own, which is exactly what "inside a transaction, every query uses the checked-out client" (rule 5) forbids. The accepted cost is that a crash partway through a load leaves a partially-seeded organization rather than rolling back atomically — a trade this codebase makes deliberately in favor of reusing tested, guardrail-compliant service code rather than writing a second, SQL-only seeding path that could drift from the first.

**A mid-pipeline state is reached by calling the pipeline's own persistence seam, not by re-running the pipeline.** AP-Flow's capture pipeline needs OCR, PII detection, and a vision model call to reach `EXTRACTED`; the seeder does not run any of that. It calls `apFlowDocumentService.savePipelineResult` directly with a canned extraction, landing the exact row shape and FSM transition the real pipeline would produce, with none of the pipeline's external dependencies. This works because the codebase already separated "do the extraction" from "persist the result" as two functions — the seam existed for testability (`extractionService` is unit-tested with a stubbed vision client) and turned out to be exactly what a deterministic seeder needed too. Where no such seam existed and the real side effect couldn't be faked without lying about it — TaxGuard's embedding, which needs a real provider — the seeder does not fake the end state; it creates the row honestly and leaves it `PENDING`, the same state a user would see before configuring a key.

## Why we chose it here

| Option | Trade-off | Verdict |
|---|---|---|
| A `pg_dump`/SQL script of an already-seeded database | Fast to generate once, but a schema change silently breaks it with no compiler or test to catch the drift, and it bypasses every trigger and FSM the live system depends on | Rejected |
| Raw `INSERT`s built by hand, matching the schema | No dependency on services being correct or stable; but proves nothing about the services, and a column added to a table needs the seeder updated in lockstep with no structural link forcing that | Rejected |
| A shared, always-on demo tenant seeded once at deploy time | Best pure showcase — nothing for a visitor to click before seeing data | A new tenancy concept (a shared org nobody owns) cutting against the org-per-registration model this suite already has; deferred, not ruled out |
| Replay through the real services, from human-readable fixture files (chosen) | Slower to write (the seeder has to satisfy every validation the real service enforces) and slower to run (a real transaction and a real trigger per row, not a bulk copy); buys a demo dataset that is provably a real, standards-compliant financial history, and a seeder that breaks loudly — as a real `ApiError`, not a silent constraint violation — the moment a service's contract changes | **Chosen** |

The general principle this generalizes to: **when the thing you're generating test/demo data *for* is itself the guarantee under test — an invariant, an audit trail, a state machine — generate the data through the code that owns that guarantee, not around it.** A fixture that bypasses the mechanism it's meant to exercise can look identical to a passing case while proving nothing.

## Where it lives in this codebase

- `sandbox/` (repo root) — the fixture folder: `manifest.json`, one subfolder per app, all dates relative and all money decimal strings.
- `server/src/services/sandbox/sandboxManifest.ts` — `loadFixture`/`loadManifest` (read + zod-validate), `resolveMonth` (the relative-offset date resolver), `addDays` (genuine calendar arithmetic for due dates, deliberately separate from `resolveMonth` — see Gotchas).
- `server/src/services/sandbox/sandboxService.ts` — the orchestrator: claims one `sandbox_datasets` row (`UNIQUE (org_id)`, the database-enforced one-load guarantee), then calls the seven `seedSandbox` functions in dependency order.
- `server/src/services/<app-slug>/sandboxSeed.ts` — one per app, seven files, each importing only its own app's services.
- `server/src/services/ap-flow/apFlowDocumentService.ts` — `savePipelineResult`, the persistence seam the seeder reuses; `createApFlowDocument`'s new `{ skipEnqueue: true }` option, added specifically so seeding a canned result can't race a real worker's genuine (and, with no key configured, failing) extraction attempt on the same document.

## Gotchas

- **A helper meant for one kind of date arithmetic will silently produce nonsense if reused for another.** `resolveMonth`'s `day` parameter is capped at 1–28 by design (so every resolved date is valid in every month, including February) — it answers "day D of month-offset O." A due date is "N days after a real date," a completely different operation, and using `resolveMonth(offset, 5 + paysInDays)` for it overflows past 28 for any payment term longer than about three weeks, throwing at runtime rather than producing a wrong-but-plausible date. The fix was a second, genuinely separate function (`addDays`) doing real calendar arithmetic via `Date.UTC`, not a wider cap on the first one — two questions need two functions, even when they both return a date string.
- **A service's own candidate query can silently exclude the exact rows a seeder is trying to feed it.** Bank-line auto-matching only ever considers an invoice or bill with `amount_due_cents > 0` — genuinely correct production behavior (an already-settled document isn't a reconciliation candidate). A seeder that pays every invoice directly and *then* imports a bank statement built from those payments leaves nothing open for the matcher to find; it silently falls back to a same-amount, different-date candidate and every suggestion scores low. The fix wasn't in the matcher — it was recognizing that seeding needs to model the *real workflow* (leave the target documents open, let reconciliation itself create the payment) rather than a shortcut that happens to produce the same final row count.
- **A service that always does more than the one thing you called it for will surprise a caller that assumes it did only that.** `generatePeriods` creates the *whole fiscal year* containing a date, not just the month asked for — entirely correct for its real caller (a user pressing "generate periods" wants the whole year), but a seeder looping it once per real month across a 24-month, 3-calendar-year window also creates a dozen empty periods for calendar months the dataset never touches. Silently trusting "the periods I just generated" without filtering to the dataset's own real date range meant a later step — "close all but the most recent 4" — closed a month that actually had data and left an empty future month open. The fix was filtering to the intended range *before* deciding what to act on, not changing the service.
- **Every one of the three bugs above was invisible until the seeder actually ran against a live database.** `npm run typecheck` and even a careful read of each service's contract caught none of them — they are runtime, cross-service interaction bugs, the exact class of defect a real, end-to-end dry run exists to surface before a demo does it in front of someone.

## Interview Q&A

**Q: Why not just write raw SQL for a seed script — isn't it simpler and faster?**
A: Simpler and faster to write, yes, but it proves nothing about the system it's seeding. This codebase's balance invariant lives in a database trigger, document immutability lives in another trigger, and every state transition lives in an application-level FSM the service layer enforces — none of that fires on a bare `INSERT`. A seed script built that way could insert an unbalanced ledger and nothing would object, which defeats the entire point of having those guarantees. Going through the real services costs more code and more runtime, but it means the seeded data is provably real by the same standard any user-entered data is held to.

**Q: How do you keep 24 months of fixture data from going stale?**
A: Every date in every fixture file is relative — a `monthOffset` from an anchor month resolved at load time, never an absolute calendar date. The anchor defaults to whatever month it's actually run in, so the dataset always looks like "the last two years," regardless of when someone loads it. The only two exceptions worth naming are money (which is a decimal string, not a date, and doesn't rot) and the exchange-rate fixture, which needed enough distinct data points across the window that any anchor month still produces a full 24-month rate history — a fixed 24 monthly rates keyed by the same relative offsets as everything else.

**Q: What happens if the seeder crashes halfway through?**
A: It leaves a partially-seeded organization — there is no outer transaction wrapping the whole load, deliberately, because each called service already owns its own transaction and wrapping them again would mean those services running off a connection they didn't check out (the same rule that governs every multi-step write in this codebase). The accepted repair path is the same one this codebase already uses for any bad data: fix it by hand, or delete the organization and reload. A single all-or-nothing wrapper was considered and rejected because it would require either bypassing the real services (defeating the entire premise) or building a second, parallel seeding mechanism with its own correctness burden.

**Q: You mention finding real bugs while building this. Walk me through one.**
A: The bank-reconciliation one is the clearest. My first pass paid every invoice and bill directly, then built a bank statement CSV from those payments, expecting the real 40/30/30 matching engine to score most of them highly. Every suggestion came back around 70 instead of clearing the 85 auto-match threshold. The candidate query the matcher runs only considers documents with a positive amount still due — by the time the statement imported, every document I'd built the CSV from was already fully paid, so the matcher was quietly falling back to unrelated same-amount candidates from a different month. The fix was recognizing the seeder needed to model the actual user workflow — leave the target invoices open, let the bank import and an explicit `matchTransaction` call be what creates the payment — rather than trying to shortcut to the same end state a different way.

**Q: Would this approach scale to a much larger fixture set, or a much bigger seed?**
A: The approach scales in complexity roughly with the number of distinct business workflows being demonstrated, not with the row count — 24 months of one customer's invoices costs the same design effort as 2 months, because the interesting work is making sure the *shape* (churn, FX exposure, an unapproved bill, a draft invoice) exercises every code path a reviewer would want to see, not generating more rows of the same shape. Runtime does scale linearly with row count, since every row is a real service call and a real transaction — for an order-of-magnitude larger seed, the next step would be moving the load onto the existing background-job queue rather than serving it synchronously over HTTP, which is a scope decision, not a redesign.

## Follow-ups they'll dig into

- "What stops someone from loading the sandbox dataset twice into the same org?" A database-level `UNIQUE (org_id)` constraint on the one marker table this feature owns, claimed in its own statement *before* any seeding starts — a 409 on the second attempt, not a service-level check that could race.
- "Why does AP-Flow need a new `skipEnqueue` option but TaxGuard doesn't?" AP-Flow's seeder supplies its own canned result immediately after creating the document, so a real worker processing the normally-enqueued job concurrently would race two writers against the same rows. TaxGuard's seeder supplies nothing after creating its row — it leaves the corpus honestly `PENDING` — so there's nothing for the normal enqueue to race against; letting the real job attempt real ingestion (and succeed once a provider is configured) is exactly the desired behavior, not a bug to guard against.
- "How would you test the seeder itself, as opposed to using it to generate test data?" The same way any other module in this codebase is tested, and it is: `__tests__/platform/sandbox.test.ts` loads the real dataset against real Postgres and asserts the seeded ledger balances, `runIntegrityChecks` passes, the FSM states land where expected, and org B sees none of org A's rows. It also asserts the *shape* of the data, not just row counts — real cohort decay, a non-zero FX-exclusion count, both bank-match outcomes, both close-run outcomes — because a fixture regression could otherwise empty the demo while every count-based assertion still passed. The trade is honesty for speed: that file takes about four minutes, since it performs several full 24-month loads through the real service layer.
