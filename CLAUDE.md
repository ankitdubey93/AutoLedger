# AutoLedger — CLAUDE.md

AutoLedger is a suite, not one app: a shared identity/tenancy platform hosting **seven portfolio applications**, each demonstrating a different accounting or engineering skill.

| App | Slug | Domain | Core skills |
|---|---|---|---|
| LedgerCore | `ledger-core` | Core Accounting & Systems | Double-entry enforced by DB trigger, immutable ledger, multi-currency FX, bank reconciliation with confidence matching, QuickBooks API sync — [docs/ledger-core.md](docs/ledger-core.md) |
| TaxGuard AI | `taxguard` | Compliance & AI Workflows | RAG, vector databases, tax act parsing |
| AP-Flow | `ap-flow` | Operational Accounting | Multimodal OCR invoice parsing, PII pixel masking, history-driven COA mapping, human-in-the-loop review — [docs/ap-flow.md](docs/ap-flow.md) |
| FP&A Engine | `fpa-engine` | Financial Modeling | 3-statement linking, scenario modeling, cash runway forecasting |
| UnitEcon | `unitecon` | Commercial Analytics | Cohort retention matrices, LTV/CAC ratios, Price-Volume-Mix variance |
| BoardDeck Automator | `boarddeck` | Board Reporting & Close | Monthly close automation, BvA variance, automated `.pptx` deck generation |
| ForecasterPro | `forecaster` | Budgeting & Planning | Driver-based rolling forecasting, headcount planning, zero-based budgeting |

LedgerCore is the only app with real routes (`status: 'building'` in `server/src/config/apps.ts`); the other six are `'planned'` — visible on the chooser, not yet built.

- **Phase 4** — live statements and fiscal periods, closing out LedgerCore GL completion. - **Phase 6** — LedgerCore bank reconciliation. Migration 019: `bank_statement_imports`, `bank_transactions` (signed `amount_cents`, `UNIQUE (org_id, dedupe_hash)` for idempotent re-import, a `to_jsonb`-row-diff immutability carve-out mirroring `payments`), `bank_match_suggestions` (up to 5 scored candidates per line, deliberately **not** audited — derived data, regenerated wholesale on every rescore). The 40/30/30 confidence engine (`utils/matchScore.ts`) scores each unmatched line against open invoices/bills within ±30 days — amount (40, exact-cents only), date proximity (30, stepped), counterparty text similarity (30, with a noise floor so coincidental letter overlap never reads as signal) — storing the full breakdown, never just the total. `AUTO_MATCH_THRESHOLD` is 85, set high because a false auto-match posts a real payment against the wrong document. `paymentService.createPayment`/`voidPayment` split into `*OnClient` halves (mirroring `journalService`) so matching/unmatching post or void a payment and update the bank line's status in one transaction — never a direct write to `journal_entries`/`ledger_lines`. `BANK_TRANSACTION_TRANSITIONS` is the first FSM here where a non-terminal reverse edge (`MATCHED → UNMATCHED`) carries a GL side effect. `/api/v1/ledger-core/bank-imports` (3 routes), `/bank-transactions` (7 routes: list, get, rescore, match, unmatch, ignore, unignore), `GET /reports/bank-reconciliation` (a **completeness** claim about the import, not a correctness claim about the books — unlike `/ar-aging`/`/ap-aging`'s `reconciles`). - **Phase 7** — shared background jobs and LedgerCore's first outbound integration, financial-event webhooks. Two dependencies, scheduled since Phase 0: `bullmq` + `ioredis`. `npm run worker` starts a second process (own event loop, own `pg` pool, own crash domain) consuming `integrity-check`, `outbox-drain`, and `webhook-deliver` queues, plus a `dead-letter` queue nothing consumes by design — a terminal job failure lands there via the worker's own `'failed'` listener, not BullMQ itself. Migration 020 (platform-tagged): `outbox_events` (written on the **caller's own transaction client**, never `pool`, so an event commits or rolls back atomically with the financial fact it describes — the mechanism guardrails rule 5 has required since Phase 0), `webhook_endpoints` (`secret` stored in plaintext, never selected into any API response), `webhook_deliveries` (one row per event per subscribed endpoint; `UNIQUE (event_id, endpoint_id)` + `ON CONFLICT DO NOTHING` makes fan-out idempotent). A 5-second repeatable drain claims unpublished events with `FOR UPDATE SKIP LOCKED`, fans them out, and separately re-enqueues any `PENDING` delivery whose Redis job looks lost — honest at-least-once delivery, never exactly-once. Migration 021 adds `ledger_settings.unmatched_alert_threshold_cents` (`DEFAULT 0` = disabled). Five events, chosen to be testable end to end: `invoice.issued`, `bill.approved`, `payment.recorded` (emitted from `paymentService.createPaymentOnClient`, so a bank-match-born payment fires identically to a manual one), `fiscal_period.closed` (on `CLOSED` only), `bank.large_unmatched` (signed amount compared by `Math.abs`). - **Phase 8** — the multi-currency FX engine, LedgerCore's last GL-completion phase. Five migrations, 022–026. `fx_rates` (022) — org-scoped, `(from_code, to_code, rate_date)`, resolved as the **latest rate on or before** a date, never an exact match; `rate` is `NUMERIC(18,8)` and stays a string end to end (never branded like `Cents`, never touched by `Number()` outside one chokepoint, `utils/fxRate.ts`'s `rateNumerator`). Migration 023 redefines migration 004's balance-invariant function (`CREATE OR REPLACE FUNCTION`, not an edit to the applied file) so **base currency is what balances**: the native-currency sum is checked only when an entry is single-currency, the base-currency sum is checked unconditionally, and a new CHECK (`chk_ledger_lines_base_matches_rate`) proves every line's `base = round(native × rate)` with zero backfill, since every existing row was already at rate 1. Migrations 024–025 add `fx_rate`/`base_*_cents` to `invoices`/`bills`/`payments`; each document resolves and freezes its own rate at issue/approve/post, re-resolved for the actual posting date, never trusted from an earlier draft save. `paymentService.createPaymentOnClient`'s realized-FX settlement is one imbalance-as-plug computation (`Σ base debits − Σ base credits`) with no direction-specific sign branch — the same subtraction produces a receivable-settled-high gain and a payable-settled-high loss; a multi-document payment posts one control line per allocation, each at *that document's own* frozen rate, never the payment's settlement rate. `payment_allocations.base_amount_cents` is this codebase's one deliberate stored-not-derived exception, pinned at write time so the subledger ties to the GL to the cent forever. Migration 026 adds `fx_revaluations`/`fx_revaluation_lines` — no status column, no FSM, a revaluation posts once and is corrected by the next one, never edited; `fxRevaluationService.runRevaluation` restates open foreign-currency AR/AP through a single `6820 Unrealized FX Gain/Loss` account and immediately posts an automatic next-day reversal, so a later realized settlement always compares against a document's original frozen rate. `/api/v1/ledger-core/fx-rates` (4 routes), `/fx-revaluations` (3 routes, `OWNER`/`ADMIN`-only post), `GET /reports/fx-exposure` (the identical computation, read-only). Bank reconciliation stays base-currency-only, a Phase 6 limit this phase does not lift. Client: `FxRatesPage`, `FxExposurePage`, `FxRevaluationsPage` (post gated by `ConfirmDialog`, matching every other irreversible action), a currency selector on invoice/bill/payment forms with a live resolved-rate/base-total preview, a new Currency sidebar group. Zero new dependencies. **The worked example in [docs/ledger-core.md § 3](docs/ledger-core.md#3-realized-fx--the-worked-example) reproduces to the paisa in a named test.** **776 server tests** (up from 717) **+ 150 client tests** (up from 144) (see [docs/roadmap.md](docs/roadmap.md#phase-8-as-delivered)).

- **Phase 9.5** — the Document Vault, a half-step (renumbers nothing). Migration 030 (platform): `documents` (`org_id`, `sha256` CHAR(64) CHECK'd to lowercase hex, `byte_size`, `mime_type` CHECK'd to a 4-type allowlist, `original_filename`, `uploaded_by`; `UNIQUE (org_id, sha256)` makes upload idempotent per tenant) and `document_links` (`org_id`, `document_id`, `app_slug`, `entity_type`, `entity_id`, `created_by`; composite FK `(org_id, document_id) → documents (org_id, id)`, so a cross-tenant link is unrepresentable). **`entity_id` carries no `REFERENCES`, deliberately** — checking it would mean the platform querying an app's own tables (rule 16); a link can outlive its entity, accepted and tested. Both tables update-immutable by trigger (`reject_document_mutation()`, `0A000`) — **not insert-only**: `DELETE` stays legal, refused by the service (`409`) while any link exists. `services/storageService.ts` (`put`/`get`/`stat`) is the entire filesystem-touching surface — org-keyed, content-addressed, two-level hex fan-out (`server/storage/<org_id>/<ab>/<cd>/<sha256>`, gitignored), so two tenants uploading identical bytes get two blobs rather than one shared blob that would leak cross-tenant existence. The blob is written **before** the database row (rule 5: no post-`COMMIT` follow-up work), so a crash leaves at worst an inert orphan on disk, never a row lying about bytes that don't exist; deletion leaves the blob too, for the same reason in reverse. `utils/mimeSniff.ts` decides the MIME type from magic bytes — PDF/PNG/JPEG by signature, CSV by a UTF-8-round-trip text check — never from the client's `Content-Type` header; `file-type` was refused as a dependency, hand-written instead like `utils/csv.ts`. `middleware/upload.ts` scopes `multer`'s memory storage to the one upload route, never registered globally beside `express.json`. `/api/v1/documents` (7 routes: upload, list filtered by app/entity, get, streamed download with `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`, attach, detach, delete) is platform-level, not namespaced under `/ledger-core`. Client: `DocumentsPage` (a suite-level destination beside `/account`) and `components/AttachmentsPanel.tsx` — a reusable panel dropped onto LedgerCore's invoice, bill and journal-entry detail pages, the cross-app proof the service is genuinely platform-level. Two new dependencies: `multer`, `@types/multer`. **868 server tests** (up from 811) **+ 172 client tests** (up from 161) (see [docs/roadmap.md](docs/roadmap.md#phase-95-as-delivered)).
- **Phase 10** — AP-Flow's capture & extraction, the suite's first app beyond LedgerCore to ship real routes (`config/apps.ts` flips `ap-flow` from `'planned'` to `'building'`). **Produces a draft; posts nothing to the ledger** — that's Phase 11's. Migration 031: `ap_flow_documents` (registers a vault document for processing; a four-state FSM — `PENDING/PROCESSING/EXTRACTED/FAILED` — with **no terminal state anywhere**, because nothing here has posted to the GL yet), `ap_flow_pages` (rasterized/redacted page metadata, deliberately unaudited — derived output, regenerated wholesale on re-extraction, the `bank_match_suggestions` ruling), `ap_flow_extractions` (**one current extraction per document**, `DELETE`-then-`INSERT` on re-extraction rather than an append-only history — both `ap_flow_pages`/`ap_flow_extractions` update-immutable by trigger, `DELETE` legal). Four dependencies, all pre-approved for this phase: `tesseract.js` (**local** OCR — PII is masked before any image leaves the machine), `sharp` (rasterizing/masking image buffers), `pdfjs-dist` (PDF page rendering; `@napi-rs/canvas` rides along as its own transitive `optionalDependency`, never imported directly), `@anthropic-ai/sdk` (vision extraction, forced into a `record_invoice` tool call rather than free-form JSON). The pipeline (`queue/handlers/apFlowExtractHandler.ts`, an event-driven `ap-flow-extract` job, no repeat schedule) runs strictly rasterize → local OCR → detect PII (hand-written Luhn/Verhoeff checksums, not digit-count matching) → mask (destructive pixel compositing) → **only then** vision extraction on the redacted bytes — `redactionService.ts` is unprefixed, shared infrastructure. Money crosses the vision boundary as decimal strings, never JSON numbers; an arithmetic mismatch is flagged (`arithmeticOk: false`), never silently accepted or auto-rejected, since nothing exists yet to protect by rejecting. `/api/v1/ap-flow/documents` (5 routes: register, list, get, redacted page image, re-extract). Client: `ApFlowDocumentsPage`, `ApFlowDocumentDetailPage` (the redacted preview captioned as exactly that — "this is the image sent to the model" — plus per-field confidence, an arithmetic warning panel, `Re-extract` gated by `ConfirmDialog`); deliberately thin, no review-queue affordances (Phase 11's). One client-side promotion recorded the same way the server's file-storage promotion was: `BackLink.tsx`/`ConfirmDialog.tsx`/`money.ts` moved from `Pages/ledger-core/` to `components/`/`utils/`, since AP-Flow needed all three and importing from another app's page directory would mirror a rule-16 violation. **932 server tests** (up from 868, plus 1 gated E2E case reporting as skipped) **+ 181 client tests** (up from 172) (see [docs/roadmap.md](docs/roadmap.md#phase-10-as-delivered)).

Next is Phase 11 (AP-Flow — mapping, review & posting), **not built**; QuickBooks sync was deferred from 9 to 17. No expense-claim/employee-reimbursement document (there is no such thing in AutoLedger, by design), no credit notes, no vendor credits, no partial void, no PDF export, no year-end closing journal entry (retained earnings stays derived), no retention/partitioning on `audit_logs` or `webhook_deliveries`, no bank feeds/OFX/QIF/MT940 beyond CSV, no bank line settling more than one document in a single match, no multi-currency bank statements (Phase 6's limit, unchanged by Phase 8 — bank matching stays base-currency-only), no external FX rate-feed integration (rates are entered by hand or imported as a batch; nothing calls out to a live provider), no currency on an *account* itself, no Redis-backed per-account rate limiting (the login/register limiter is still per-IP; `rate-limit-redis` is not an approved dependency), no `payment.voided` webhook event or custom event types, no `POST /webhooks/:id/test`, no open-item (per-customer/per-vendor) or foreign-currency opening-balance import, no database-level immutability trigger on a `COMMITTED` migration import (the service refuses every write past that point; nothing yet stops a raw `UPDATE` the way `invoices`/`bills`/`payments` are stopped), no suite-level onboarding wizard UI (the `'platform'` onboarding row exists and is tracked; only LedgerCore's app-level wizard has a page). **The Document Vault has no object storage** (filesystem only, does not survive a multi-instance deployment), **no virus scanning, no thumbnail/preview generation, no document versioning, no blob garbage collection** (a deleted document's blob stays on disk forever), and **no per-document permissions finer than organization membership**. **AP-Flow posts nothing to the GL, has no COA mapping/tax split/FX-at-invoice-date/review queue, no `ap_flow_line_items` table** (line items stay JSONB until Phase 11), **and no measured PII-detection recall figure** — the honest claim is "redaction pipeline implemented," never "PII cannot leak." See [docs/roadmap.md](docs/roadmap.md) and the ladder in [docs/ledger-core.md](docs/ledger-core.md) / [docs/ap-flow.md](docs/ap-flow.md). The other five apps have no routes.

## Hard rules

Violating any of these is a bug, not a style choice. Full detail and code examples: [docs/guardrails.md](docs/guardrails.md).

1. **Every query is scoped by `org_id`.** No `org_id` predicate = tenant data leak. `user_id` is a `created_by` audit field, **never** an access check. Read the active org only from the verified access token — never a header, param, or body. The app slug in the URL is a routing namespace, not a tenancy boundary — see rule 16.
2. **No SQL in controllers.** Controllers validate input, call a service, format the response. All `pool.query` / `client.query` lives in `src/services/` — including auth and the app registry.
3. **Money is integer `BIGINT` cents.** Never floats, never `DECIMAL`. `isBalanced` is integer equality, never an epsilon comparison.
4. **Parameterized queries only** (`$1, $2`). Never interpolate into SQL — whitelist identifiers like sort columns against a constant map.
5. **Inside a transaction, every query uses the checked-out `client`.** A stray `pool.query` silently escapes the transaction. No post-`COMMIT` follow-up work — queue it.
6. **Posted financial documents are immutable.** Correct via reversing entries (`POST /:id/reverse`). No `PUT`/`DELETE` on a posted journal, invoice, receipt, or payroll run. From Phase 3 a `BEFORE UPDATE OR DELETE` trigger enforces this in the database too.
7. **A ledger line has exactly one side populated**, and an entry balances. Both sides > 0 is invalid; both zero is invalid. Enforce in the service *and* with a CHECK constraint; the entry-level balance is re-checked by a `DEFERRABLE INITIALLY DEFERRED` constraint trigger at `COMMIT`.
8. **Every `*_id` gets a `REFERENCES` constraint** with explicit `ON DELETE`. Index every FK used in a join and every scope column.
9. **Emails lowercase on write**, backed by `UNIQUE (LOWER(email))`.
10. **Lifecycle status lives in one FSM transition table** in code. No ad-hoc status assignment scattered across services.
11. **Tokens:** `ACCESS_TOKEN_SECRET` (15m) and `REFRESH_TOKEN_SECRET` (7d). There is no `JWT_SECRET` — do not reintroduce it. Never log decoded payloads.
12. **Account types are exactly five:** `Asset`, `Liability`, `Equity`, `Revenue`, `Expense`. Never a sixth.
13. **Migrations:** `server/src/db/migrations/` only, sequential 3-digit prefix, additive and idempotent. **Never edit an applied migration.** Destructive changes need explicit sign-off. One shared sequence across every app — filenames tag the app: `NNN_<app-slug>_<subject>.sql`.
14. **No dependency before the phase that needs it.** No ORM. Redis-backed queueing (`bullmq` + `ioredis`) landed in Phase 7 — see the Phase 7 bullet above; don't add a third queue-adjacent package (e.g. `rate-limit-redis`) speculatively. The blanket "no LLM" ruling is reversed for exactly two apps: AP-Flow's vision extraction (Phase 10) and TaxGuard AI's RAG (Phase 16). No LLM/embeddings SDK outside those — see [docs/roadmap.md](docs/roadmap.md#phase-renumbering--2026-09-01).
15. **Every module ships tests**, including a cross-tenant isolation test. Without one it is not done — one per app, not one for the whole suite.
16. **App boundaries are namespaces, not tenancy.** `org_id` is still the only access-control boundary inside an app's own routes. No app reads another app's tables directly — cross-app effects go through LedgerCore's GL via `source_type`/`source_id`. `config/apps.ts` is the single source of truth for which slugs exist.
